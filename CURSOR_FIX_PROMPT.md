Репозиторий: desktop-приложение на PySide6 (Python) для прошивки STM32 + firmware на C (STM32 HAL). Ниже — полный список подтверждённых находок из двух независимых аудитов (Python-часть и firmware/application), с точными файлами/строками и требуемым фиксом. Исправляй по порядку приоритета, каждый пункт — отдельным логическим изменением. После каждого фикса перепроверяй, что не сломал смежную логику (особенно протокол между ПК и устройством — байтовый формат менять НЕЛЬЗЯ, кроме явно указанных случаев).

## 🔴 ПРИОРИТЕТ 1 — блокирует CI, чинить первым

### 1.1 Сломанный `ruff.toml` — падает вся сборка (Windows/macOS/Linux)

**Файл:** `ruff.toml`

Сейчас:
```toml
line-length = 120

[lint]
select = ["E9", "F"]
extend-exclude = [
    "firmware/libs/**",
    "assets/version_info.py",
]
```

`extend-exclude` — это top-level ключ конфигурации ruff, а не lint-специфичный. Из-за того, что он вложен в `[lint]`, `ruff check .` падает с ошибкой парсинга TOML (`unknown field 'extend-exclude'`). Так как `.github/workflows/build.yml` теперь запускает `ruff check .` перед сборкой во всех трёх build-джобах, любой push в `main` ломает релизный пайплайн целиком.

**Исправить на:**
```toml
line-length = 120
extend-exclude = [
    "firmware/libs/**",
    "assets/version_info.py",
]

[lint]
select = ["E9", "F"]
```

**Проверка:** выполнить `ruff check .` в корне репозитория — должно завершиться без ошибки парсинга конфига (реальные находки lint допустимы, но парсинг файла конфигурации обязан пройти).

## 🔴 ПРИОРИТЕТ 2 — функциональный блокер в новой firmware (никогда не собиралась и не тестировалась на железе)

### 2.1 `trigger_t` не кратен размеру полуслова → триггеры не переживают перезагрузку устройства

**Файлы:** `firmware/application/Inc/trigger.h` (структура `trigger_t`, строки ~35-53), `firmware/application/Src/trigger.c` (`flash_write_all_triggers`, `Trigger_Init`)

Проблема: `sizeof(trigger_t)` фактически равен **53 байтам** (packed-структура), а не 48, как написано в комментарии `trigger.h` (`/* 48 bytes, fits 10x in the 2KB page with room to spare */`) и в `firmware/PROTOCOL.md` (там же указано "10 × 48 байт").

В `flash_write_all_triggers()` (`trigger.c`) число полуслов для `HAL_FLASH_Program` вычисляется как `sizeof(trigger_t) / 2U` — целочисленное деление даёт `53/2 = 26`, то есть **физически записывается только 52 байта из 53** (теряется последний байт — поле `crc8`), и адрес следующего слота увеличивается на эти же 52 байта.

При этом `Trigger_Init()` при чтении индексирует слоты с шагом **`sizeof(trigger_t)` = 53 байта**.

Результат: шаг записи (52) не совпадает с шагом чтения (53) → после первой же записи триггера через `CMD_TRIGGER_WRITE` и следующей перезагрузки устройства все 10 слотов читаются со сдвигом, `crc8`/`magic` не совпадают, и firmware тихо считает все триггеры сброшенными в дефолт — без единой ошибки на ПК. Функция триггеров работает только в рамках одной сессии до сброса питания.

**Исправить:**
1. Сделать `sizeof(trigger_t)` кратным 2 (чётным), например увеличив `reserved[3]` до `reserved[4]` в `trigger.h` — это даст 54 байта (кратно 2).
2. Убедиться, что и запись (`flash_write_all_triggers`), и чтение (`Trigger_Init`) используют **один и тот же** актуальный `sizeof(trigger_t)` как шаг — не пересчитывать вручную, использовать константу `sizeof(trigger_t)` в обоих местах, без деления с потерей остатка. Если деление на 2 для получения количества half-word используется — обязательно через `(sizeof(trigger_t) + 1U) / 2U)` ИЛИ гарантировать чётность структуры и не терять данные.
3. Проверить, что `10 * sizeof(trigger_t)` (после фикса — 540 байт) всё ещё помещается в `TRIGGER_PAGE_SIZE` (2048 байт, страница 0x0803E000) — помещается с запасом.
4. Обновить комментарий в `trigger.h` (заменить "48 bytes" на реальный размер после фикса) и таблицу в `firmware/PROTOCOL.md` (заменить "10 × 48 байт" на актуальное значение).
5. Написать/прогнать простой unit-тест (можно на хосте, не на плате) — эмулировать `flash_write_all_triggers`+`Trigger_Init` над буфером в памяти и убедиться, что все 10 слотов после "записи+чтения" совпадают побайтово с исходными данными, включая корректный `crc8`.

**Не менять** формат TLV-команд `CMD_TRIGGER_READ`/`CMD_TRIGGER_WRITE` в `protocol.c` — там `sizeof(trigger_t)` уже передаётся как единое целое и работает корректно, проблема только в персистентном хранении во Flash.

## 🟠 ПРИОРИТЕТ 3 — реальные баги, оставшиеся неисправленными с прошлого аудита

### 3.1 Хардкод `page_size = 2048` при чтении конфигурации (запись уже исправлена, чтение — нет)

**Файл:** `ui/flash_dialog.py`, метод, содержащий:
```python
page_size = 2048
start = flash_size_kb * 1024 - page_size
```
(это в обработчике кнопки "Читать конфигурацию" — там же, где создаётся `ReadWorker(method, self._config, size=page_size, start=start, ...)`)

В этом же файле уже есть метод `_get_page_size()`, который корректно определяет размер страницы Flash по модели MCU (используется в `_prepare_config_only_hex` и `_prepare_firmware_with_config`). Эта же логика не применена в пути чтения конфигурации.

**Исправить:** заменить `page_size = 2048` на вызов существующего `self._get_page_size()` (обернуть в `try/except ValueError` по аналогии с тем, как это уже сделано в других местах файла — показать `QMessageBox.warning` и `return` при ошибке). Проверить, что после фикса чтение конфига на F103 (page=1024) и F2/F4 (page=16384) вычисляет правильный `start`.

### 3.2 Дублирование serial-протокола в `ui/flash_dialog.py` вместо переиспользования `SerialManager`

**Файл:** `ui/flash_dialog.py`, классы `ConnectWorker`, `FlashWorker`, `ReadWorker`

Каждый из этих трёх классов независимо делает `import serial as serial_module` и напрямую открывает/пишет/читает `serial.Serial(...)`, минуя уже существующий `core/serial_manager.py::SerialManager`, который содержит потокобезопасную (после недавнего фикса с RLock) логику работы с портом. Также `main.py` в `_cli_flash` делает то же самое отдельно, независимо.

**Исправить:** отрефакторить эти три worker-класса так, чтобы они использовали общий слой доступа к порту (либо через `SerialManager`, либо выделив единый низкоуровневый helper-класс в `core/`, которым пользуются оба места — GUI и CLI). Цель — единственное место, где происходит `serial.Serial(...)` открытие/запись/чтение порта для операций прошивки, чтобы устранить риск разного поведения (таймауты, обработка ошибок, локи) между путями.

Это самая объёмная правка — если не успеваешь сделать полный рефакторинг, как минимум:
- вынести повторяющийся код открытия порта с таймаутами/ретраями в одну функцию в `core/` и вызывать её из всех четырёх мест (3 worker-класса + `main.py`);
- добавить хотя бы базовые unit-тесты на протокольную логику без реального порта (замокать `serial.Serial`), используя уже существующий `core/fake_serial.py` как основу.

### 3.3 `core/bootloader.py::erase_pages` без защиты от избыточного стирания

**Файл:** `core/bootloader.py`, функция `erase_pages` (сигнатура вида `erase_pages(self, ..., page_size: int = 2048, flash_base: int = 0x08000000)`)

В отличие от `core/dfu.py`, где `erase_pages` принимает параметр `skip_blank: bool = True` и не стирает страницы, которые уже полностью `0xFF` (пустые), UART/bootloader-путь стирает страницы всегда, без проверки. При повторном вызове (например, после сбоя связи и повторной попытки прошивки) это увеличивает количество циклов erase на Flash без необходимости и увеличивает риск обрыва питания/связи ровно в момент стирания уже корректных страниц.

**Исправить:** добавить в `core/bootloader.py::erase_pages` тот же параметр `skip_blank: bool = True` и логику проверки "страница уже пуста — не стирать", по аналогии с реализацией в `core/dfu.py`. Убедиться, что вызывающий код (`ui/flash_dialog.py`) передаёt этот параметр так же, как для DFU-пути, если там предполагается одинаковое поведение.

### 3.4 Несогласованность базовых адресов прошивки между методами

**Файл:** `ui/flash_dialog.py` (несколько мест: UART/USB CDC путь использует `base = 0x08008000`, ST-Link/DFU путь использует `base = 0x08000000`), `core/bootloader.py`, `core/dfu.py`

Нет единой константы/источника истины для базового адреса, и нет предупреждения пользователю, если выбранный метод прошивки не соответствует ожидаемому адресу (например, если пользователь выбрал DFU но целится в область application, а не в полный образ с bootloader).

**Исправить:**
1. Вынести адреса в явные именованные константы в одном модуле (например `core/stm32_info.py`, где уже есть `STM32_PAGE_SIZES`): `BOOTLOADER_BASE_ADDR = 0x08000000`, `APPLICATION_BASE_ADDR = 0x08008000`.
2. Использовать эти константы во всех местах вместо магических литералов.
3. Добавить в UI явную проверку/предупреждение: если пользователь через UART/USB CDC пытается прошить образ, начинающийся с адреса bootloader-области (0x08000000), или через ST-Link/DFU пытается прошить в адрес application без явного намерения перезаписать весь образ — показать предупреждающий диалог с объяснением, что будет перезаписано.

## 🟡 ПРИОРИТЕТ 4 — безопасность и надёжность (новые находки, не входили в предыдущий аудит)

### 4.1 `core/script_engine.py` — sandbox не является реальной изоляцией

Пользовательские Python-скрипты (для обработки CAN-кадров) выполняются через `exec()` с урезанным `__builtins__`. Такая изоляция обходится классическими способами интроспекции объектов (например, через `().__class__.__bases__[0].__subclasses__()` можно получить доступ к произвольным загруженным классам Python, включая файловые/подпроцессные, если соответствующие модули загружены где-либо в процессе).

**Исправить (минимально):**
- В README/UI редактора скриптов чётко указать пользователю, что это НЕ security sandbox, а просто ограничение по неосторожным ошибкам, и скрипты из недоверенных источников запускать нельзя.
- По возможности рассмотреть использование `RestrictedPython` или запуск в отдельном процессе с ограниченными правами (subprocess с урезанным окружением) вместо `exec()` в основном процессе — если это не критично для релиза, оставить как TODO с явным комментарием в коде `core/script_engine.py`.

### 4.2 `core/script_engine.py` — гонка данных при таймауте выполнения скрипта

При таймауте (`thread.join(timeout=3.0)`) поток-исполнитель скрипта не останавливается принудительно (Python threads не поддерживают безопасное прерывание) — он продолжает работать в фоне (daemon=True) и может продолжать писать в `self._log_lines` / `self._send_requests`. Если пользователь запускает следующий скрипт, эти атрибуты переинициализируются новыми списками, но "протухший" старый поток продолжает держать ссылку на старые объекты — либо (если он читает `self.` заново на каждой итерации) начинает писать в списки уже нового запуска.

**Исправить:** передавать зависшему потоку не `self`, а специфичный для конкретного запуска контекст/объект (например, локальные списки, созданные в момент запуска, передаваемые в поток явно как аргументы, а не через `self`), чтобы даже "протухший" поток продолжал писать в свою собственную изолированную структуру данных, не влияя на следующий запуск. После таймаута — логировать явное предупреждение "скрипт не завершился в отведённое время и продолжает работать в фоне, результаты могут быть неполными".

### 4.3 `core/serial_manager.py::send_data()` — проверка состояния порта вне лока (TOCTOU)

**Файл:** `core/serial_manager.py`, метод `send_data()`

Строка вида:
```python
if self._port is None or not self.is_open():
    return False
with self._lock:
    ...
```
Проверка выполняется ДО захвата лока, тогда как весь остальной файл (после недавнего фикса гонок) методично оборачивает доступ к `self._port` в `with self._lock:`. Между проверкой и входом в блок другой поток может закрыть порт.

**Исправить:** переместить проверку `self._port is None or not self.is_open()` внутрь `with self._lock:`, чтобы вся операция (проверка + запись) была атомарной относительно лока, как и остальные методы этого класса.

### 4.4 `firmware/application/Src/can_bridge.c` — не обрабатываются ошибки/bus-off шины CAN

Активирован только `CAN_IT_RX_FIFO0_MSG_PENDING`; `CAN_IT_ERROR`/`CAN_IT_BOF` не включены, `HAL_CAN_ErrorCallback` не реализован. `AutoBusOff = ENABLE` даёт аппаратное самовосстановление, но ни firmware, ни протокол на ПК не узнают о факте bus-off/ошибок шины (например, при плохом контакте терминатора).

**Исправить:** включить `CAN_IT_ERROR` (и/или `CAN_IT_BOF`) при инициализации CAN в `can_bridge.c`, реализовать `HAL_CAN_ErrorCallback`, и передавать индикацию ошибки шины на ПК через существующий протокольный канал (либо расширив служебные команды 0x90-0x93, либо добавив новую TLV-команду по аналогии с 0xC0-0xC5 — согласовать формат с `firmware/PROTOCOL.md` и обновить документ).

### 4.5 История git содержит устаревшие персональные/внутренние файлы

Старые `.xlsx` файлы (например, файлы учёта) и `reliz1.hex` были удалены из рабочего дерева, но остаются в истории git (`git log --all --diff-filter=A --name-only` их находит в старых коммитах).

**Исправить (по желанию, обсудить с владельцем репозитория перед выполнением — это деструктивная операция):** прогнать `git filter-repo` (предпочтительно) или BFG Repo-Cleaner для полной очистки истории от этих файлов, затем force-push в удалённый репозиторий с предупреждением всем, у кого есть локальные клоны, о необходимости их пересоздать.
