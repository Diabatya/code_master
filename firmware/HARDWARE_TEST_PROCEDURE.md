# Процедура аппаратных throughput/soak-тестов CodeMaster

Документ предназначен для проверки реальной платы STM32F105RCT6 после сборки новой bootloader/application firmware.

Цель — измерить не только факт подключения, но и:

- пропускную способность CAN1/CAN2;
- потери кадров;
- USB CDC throughput;
- bus-off/error recovery;
- задержку trigger response;
- стабильность при длительной работе;
- устойчивость к отключению USB/питания;
- корректность обновления Flash и конфигурации.

---

## 1. Оборудование

Обязательно:

- плата с STM32F105RCT6;
- USB-кабель с передачей данных;
- регулируемое питание 3.3 V или штатное питание платы;
- ST-Link для восстановления bootloader/application;
- CAN-адаптер или второй STM32/CAN-генератор для CAN1;
- CAN-адаптер или второй STM32/CAN-генератор для CAN2;
- CAN-анализатор или логический анализатор;
- терминаторы 120 Ом;
- мультиметр.

Желательно:

- осциллограф;
- генератор CAN-трафика с заданной скоростью;
- USB protocol analyzer;
- второй компьютер для независимого мониторинга;
- термодатчик или камера для контроля нагрева.

## 2. Подготовка firmware

1. Собрать application:

```bash
cd firmware/application
make clean
make
```

2. Собрать bootloader:

```bash
cd firmware/bootloader
make clean
make
```

3. Убедиться, что application HEX содержит два сегмента:

```text
0x08008000 — application code
0x0803D000 — application metadata CRC32
```

4. Проверить размер и CRC metadata:

```bash
python3 firmware/tools/add_app_metadata.py \
  firmware/application/build/codemaster_app.raw.hex \
  /tmp/codemaster_app_checked.hex
```

5. Сохранить SHA256:

```bash
shasum -a 256 firmware/application/build/codemaster_app.hex
shasum -a 256 firmware/application/build/codemaster_app.bin
```

6. Сохранить резервную копию текущей прошивки платы.

## 3. Проверка загрузки и восстановления

### 3.1. Первый запуск

- [ ] Прошить bootloader через ST-Link.
- [ ] Прошить application HEX.
- [ ] Установить `BOOT0 = 0`.
- [ ] Нажать Reset.
- [ ] Проверить USB CDC application:
  ```text
  VID=0483 PID=5740
  ```
- [ ] Нажать в конфигураторе «Подключиться».
- [ ] Проверить отображение версии application и config format.
- [ ] Проверить, что bootloader передаёт управление application.

### 3.2. Проверка bootloader

- [ ] Установить `BOOT0 = 1`.
- [ ] Нажать Reset.
- [ ] Проверить USB DFU `0483:DF11` или custom bootloader `0483:5741`.
- [ ] Прочитать версию bootloader.
- [ ] Прочитать ID STM32.
- [ ] Установить `BOOT0 = 0` и перезапустить.

### 3.3. Повреждённая application

- [ ] Подготовить тестовый образ с повреждённым vector table.
- [ ] Записать его только в application-область.
- [ ] Перезапустить устройство.
- [ ] Убедиться, что bootloader не передал управление повреждённому образу.
- [ ] Убедиться, что USB bootloader остаётся доступным.
- [ ] Повторно прошить корректный application.

## 4. Проверка конфигурации

### 4.1. Прямая запись

- [ ] Запустить новую application.
- [ ] Открыть вкладку прошивки.
- [ ] Не выбирать основной firmware-файл.
- [ ] Заполнить «Устройство».
- [ ] Заполнить «Серийный номер».
- [ ] Нажать «Прошить».
- [ ] Убедиться, что используется `CMD_CFG_WRITE`.
- [ ] Зафиксировать время операции.
- [ ] Убедиться, что application не перезаписывалась.
- [ ] Убедиться, что триггеры сохранились.
- [ ] Дождаться USB-переподключения.

### 4.2. Чтение

- [ ] Нажать «Прочитать конфигурацию».
- [ ] Проверить имя.
- [ ] Проверить serial.
- [ ] Проверить config version.
- [ ] Проверить CRC8.
- [ ] Проверить VID/PID.

### 4.3. Повторная запись тех же данных

- [ ] Повторить запись без изменения полей.
- [ ] Проверить, что firmware не выполняет лишний Flash erase, если данные совпадают.
- [ ] Проверить, что USB не переподключается без необходимости.

## 5. Проверка CAN базовой работоспособности

Для каждого канала отдельно:

- [ ] Установить скорость 500 кбит/с.
- [ ] Подключить CAN-генератор.
- [ ] Запустить передачу 100 кадров/с.
- [ ] Проверить получение кадров в конфигураторе.
- [ ] Проверить счётчик `Device RX`.
- [ ] Отправить кадры обратно через UI.
- [ ] Проверить счётчик `Device TX`.
- [ ] Сверить количество кадров с внешним CAN-анализатором.

Критерий PASS:

```text
RX/TX количество совпадает с внешним анализатором.
Lost count = 0.
CAN error count = 0.
Bus-off = 0.
```

---

## 6. CAN throughput test

### 6.1. CAN1

1. Передавать максимально плотный поток стандартных CAN-кадров.
2. Зафиксировать:
   - битрейт;
   - frames/sec;
   - длительность;
   - отправленное количество;
   - полученное количество.
3. Выполнять тест минимум 10 минут.

Записать:

```text
CAN1 bitrate:
Generator frames/sec:
Device RX:
Device lost:
Device errors:
Device bus-off:
Duration:
```

### 6.2. CAN2

Повторить те же действия для CAN2.

### 6.3. Две шины одновременно

- [ ] Одновременно загрузить CAN1.
- [ ] Одновременно загрузить CAN2.
- [ ] Включить USB мониторинг.
- [ ] Включить хотя бы один trigger.
- [ ] Запустить тест на 10 минут.
- [ ] Повторить на 30 минут.

Критерий PASS:

```text
Lost count = 0 или ниже согласованного предела.
Watchdog не сработал.
USB не отключился.
CAN error/bus-off отсутствуют.
```

Если `lost_count > 0`:

- сохранить counters;
- сохранить частоту потока;
- сохранить логи;
- проверить увеличение `CAN_RING_DEPTH`;
- проверить время обработки `Protocol_Poll()`;
- проверить USB TX saturation.

## 7. Trigger timing test

### Подготовка

- [ ] Настроить trigger на ответ с задержкой 0 мс.
- [ ] Повторить для 1 мс.
- [ ] Повторить для 5 мс.
- [ ] Повторить для 10 мс.
- [ ] Повторить для 100 мс.

Для каждого режима измерить осциллографом или CAN-анализатором:

```text
Время входного кадра
Время ответного кадра
Фактическая задержка
Количество срабатываний
Максимальное опоздание
```

Критерий PASS:

- количество срабатываний совпадает с количеством входных событий;
- максимальное опоздание не превышает согласованный предел;
- нет зависания при нескольких активных triggers.

## 8. USB CDC test

### 8.1. Базовый обмен

- [ ] Подключить USB CDC.
- [ ] Прочитать system info.
- [ ] Прочитать config.
- [ ] Прочитать CAN stats.
- [ ] Прочитать trigger stats.
- [ ] Запустить CAN monitor.

### 8.2. USB при высокой нагрузке

- [ ] Создать высокую нагрузку CAN1/CAN2.
- [ ] Оставить USB monitor включённым.
- [ ] Проверить `Device RX/TX/Lost`.
- [ ] Вынимать и вставлять USB во время потока.
- [ ] Убедиться, что CAN продолжает работать автономно.

### 8.3. Отключение host

- [ ] Закрыть конфигуратор во время CAN-потока.
- [ ] Убедиться, что firmware не зависает.
- [ ] Убедиться, что watchdog не перезапускается постоянно.
- [ ] Повторно подключить конфигуратор.

## 9. Flash update fault injection

### 9.1. Отключение USB

- [ ] Начать прошивку application.
- [ ] Отключить USB на 10%.
- [ ] Проверить вход в bootloader после перезапуска.
- [ ] Повторить прошивку.
- [ ] Проверить CRC application.

### 9.2. Отключение питания

Повторить отключение питания на этапах:

- [ ] erase;
- [ ] начало записи;
- [ ] середина записи;
- [ ] последний блок;
- [ ] verification.

Критерий PASS:

```text
Bootloader всегда доступен.
Повреждённая application не запускается.
Повторная прошивка восстанавливает устройство.
```

## 10. Soak test

Минимальная длительность: 30 минут.

Режим:

- CAN1 — высокая загрузка;
- CAN2 — высокая загрузка;
- USB monitor — включён;
- один или несколько triggers — активны;
- периодическое чтение CMD_CAN_STATS;
- периодическое чтение CMD_TRIGGER_STATS;
- watchdog — включён.

Каждые 5 минут сохранять:

```text
Device RX
Device TX
Lost
CAN errors
Bus-off
Trigger fired
Max trigger lateness
USB reconnect count
Application uptime
```

Критерий PASS:

- нет самопроизвольных reset;
- нет зависания USB;
- нет неконтролируемого роста lost count;
- нет утечек памяти/деградации скорости;
- counters корректно увеличиваются;
- после переподключения USB устройство продолжает работу.

## 11. Итоговый отчёт испытаний

Для каждого теста заполнить:

```text
Дата:
Плата:
MCU:
Bootloader version:
Application version:
Protocol version:
PC OS:
USB driver:
CAN bitrate:
Оборудование:
Результат:
Проблемы:
Логи:
Скриншоты:
```

Финальный статус:

```text
[ ] PASS
[ ] PASS WITH LIMITATIONS
[ ] FAIL
```

Все FAIL должны иметь:

- шаг воспроизведения;
- входные условия;
- ожидаемый результат;
- фактический результат;
- лог;
- counters;
- информацию о прошивке и драйверах.
