# Ответ на технические вопросы по прошивке STM32F105RCT6

## Резюме

Прошивку можно реализовать, но у нас уже есть часть решения со стороны ПК, и без обратной связи по железу/протоколу готовый бинарь может не заработать на конкретной плате. Ниже — что у нас есть, чего не хватает и какие технические противоречия нужно закрыть.

## Что уже есть у нас

### 1. Загрузчик (bootloader)

- Исходники: `firmware/bootloader/`
- Сборка: `cd firmware/bootloader && make`
- Инструментарий: `arm-none-eabi-gcc` установлен (`/opt/homebrew/bin/arm-none-eabi-gcc`)
- Память:
  - Bootloader: `0x0800_0000`–`0x0800_7FFF` (32 KB)
  - Application: `0x0800_8000`–`0x0803_FFFF` (224 KB)
- Вход в bootloader из приложения: запись `0xDEADBEEF` по адресу `0x2000_4FF0` + `NVIC_SystemReset()`

### 2. USB-идентификаторы

- Bootloader: `VID=0x0483`, `PID=0x5741`
- Application: `VID=0x0483`, `PID=0x5740`

### 3. Клиентская часть на Python

- `core/bootloader.py` — работает с загрузчиком по UART/USB CDC.
- `core/can_protocol.py` — пакует/распаковывает CAN-кадры для обмена по UART-мосту.
- `core/serial_manager.py` — управление портом, приём кадров, автоопределение.
- `ui/*` — конфигуратор с триггерами, мониторингом, шлюзом и прошивальщиком.

Это означает, что формат **CAN-over-UART** у нас уже согласован на ПК-стороне.

## Что не хватает для начала разработки основной прошивки

### 1. Аппаратная схема

Необходимы **как минимум**:
- PDF/схема платы или таблица распиновки в формате Excel/CSV;
- точные выводы `CAN1_TX/RX`, `CAN2_TX/RX`;
- выводы управления `TJA1050_S` (Normal/Silent) для обоих каналов;
- выводы терминаторов `CAN1_120R`, `CAN2_120R`;
- выводы `OUT1..OUT4` с указанием типа (открытый сток / push-pull) и ограничениями по току;
- подключение USB (DP, DM, есть ли внешняя подтяжка 1,5 кОм на DP);
- кварц HSE (8 МГц) и его выводы;
- SWD (SWCLK/SWDIO);
- питание и земля.

### 2. Приложение А — протокол USB-команд

В ТЗ написано, что протокол «разрабатывается отдельно». Без него невозможно реализовать:
- чтение/запись конфигурации;
- отправку CAN;
- управление выходами;
- автоопределение скорости;
- запуск/останов циклической передачи;
- передачу ошибок/статуса.

**Варианты решения:**
- Прислать готовый протокол (документ или исходники старой/эталонной прошивки).
- Либо разрешить нам его формализовать на основе уже существующего desktop-кода. Тогда нужно 1–2 дня на аудит `core/can_protocol.py`, `core/serial_manager.py` и `ui/*`, чтобы выписать полный список команд и форматов.

### 3. Структура Flash-памяти конфигурации

Для STM32F105 страница обычно 1 КБ. Один образ конфигурации явно не влезет в 1 КБ. Нужно зафиксировать:
- сколько страниц резервировать;
- адреса страниц A, B, V;
- размер линкуer script и смещение приложения (`0x0800_8000`).

Если схемы/лейаута нет — мы сделаем условное разбиение, но потом адреса придётся согласовывать с конфигуратором.

## Технические противоречия, которые нужно решить

### 1. Пропускная способность USB vs CAN

Расчёт:

- 1 CAN-кадр до 18 байт (включая маркер, канал, ID, DLC, данные, CRC).
- 14 000 кадров/с = ~252 000 байт/с чистыми данными.
- Добавляем USB-заголовки, служебные команды, ответы — получаем больше 2 Мбит/с.

Требование «не менее 1 Мбит/с» в USB FS **недостижимо** при полной загрузке двух шин.

**Нужно выбрать одно из:**
- поднять требование до 12 Мбит/с (USB HS) или агрегировать CAN-кадры;
- разрешить потерю пакетов/прореживание;
- использовать бинарные USB bulk-пакеты с несколькими CAN-кадрами;
- разделить режим «запись всех кадров» и «автономный триггерный» режим.

### 2. Автоопределение скорости CAN

CAN-контроллер при неверной скорости генерирует ошибки, но не может гарантированно понять, что скорость правильная, пока не примет несколько валидных кадров подряд.

**Нужно задать параметры:**
- таймаут проверки каждой скорости (например, 100–300 мс);
- количество валидных кадров для признания скорости (например, 3–5);
- поведение при молчащей шине;
- список кандидатов (125, 250, 500, 1000 кбит/с и т.д.).

### 3. Запись Flash и потеря CAN-кадров

Во время стирания/записи внутренней Flash ядро STM32 останавливается на десятки миллисекунд. CAN-контроллер может продолжать приём, но кольцевой буфер на 512 пакетов легко переполнится при высокой нагрузке.

**Варианты:**
- увеличить RAM-буферы;
- выполнять обработчики CAN из RAM;
- временно отсылать NACK/PAUSE конфигуратору;
- ограничивать приём на время записи.

### 4. TJA1050 и режим Normal перед TX

Требование «переводить PB7/PB4 в Normal непосредственно перед TXRQ» технически реализуемо, но задержка должна быть проверена осциллографом. Мы предусмотрим программную задержку в несколько микросекунд, но финальная калибровка — по железу.

## Предлагаемый план

1. **Этап 0 — сбор данных (1–2 дня)**
   - Получить схему/распиновку.
   - Получить/согласовать протокол USB-команд.
   - Зафиксировать адреса Flash-страниц.

2. **Этап 1 — минимально проверяемый проект (3–5 дней)**
   - Старт из Flash по `0x0800_8000`.
   - HSE 8 МГц → 72 МГц.
   - GPIO: светодиод (если есть), TJA1050_S, терминаторы, OUT1..OUT4.
   - CAN1/CAN2: loopback + Silent/Normal.
   - USB CDC: VID/PID 0x0483/0x5740.
   - Простой эхо-протокол для проверки связи.

3. **Этап 2 — протокол конфигуратора (3–5 дней)**
   - Реализация команд на чтение/запись конфигурации.
   - CAN-триггеры, циклическая отправка.
   - Атомарная запись Flash.

4. **Этап 3 — дополнительные функции (2–4 дня)**
   - Автоопределение скорости.
   - Sleep/Stop, IWDG.
   - Watchdog, терминаторы, OUT.
   - Финальная подпись `.bin`/`.hex`.

## Если исходных данных нет

Мы можем начать с базового проекта, но он будет работать **только в симуляции/эмуляции** до проверки на реальной плате. В этом случае сообщите явно:

```
Проекта/схемы нет. Платы изготовлены по ТЗ. Делать базовый проект с условной распиновкой.
```

Тогда мы используем распиновку, близкую к оригинальному bootloader-проекту, и предупредим, что потребуется переконфигурация под конкретную плату.

1. Схема или таблица распиновки.
2. Приложение А (протокол USB-команд) или разрешение вывести его из desktop-кода.

4. Решение по пропускной способности USB.
5. Параметры автоопределения скорости CAN.

После этого срок и стоимость станут точными.
