# Application firmware — стартовый код (STM32F105RCT6)

**Статус: начальный/стартовый код, не проверен компилятором и не прошит на
реальное железо.** Написан по тексту ТЗ (разделы 8/10.2–10.3/11/12/13) без
принципиальной схемы (подтверждено пользователем: «Есть только текст ТЗ,
схемы нет»). Прежде чем прошивать реальное устройство — обязательно пройти
контрольный список в конце этого файла.

## Что это и как соотносится с остальным проектом

Это firmware для CAN/USB-моста и «триггерного» модуля, который описан в
ТЗ (physical device), а не для PySide6-конфигуратора `code_master` на ПК
(тот уже существует и не менялся). Конфигуратор общается с этим устройством
через USB CDC-ACM по протоколу, формализованному в `firmware/PROTOCOL.md`
(«Приложение А», реконструировано из `core/can_protocol.py` /
`core/serial_manager.py`, так как отдельного файла Приложения А предоставлено
не было).

Состоит из двух независимых прошиваемых образов:

- `firmware/bootloader/` — уже существовавший AN3155-совместимый USB DFU
  бутлоадер (не менялся в этой сессии).
- `firmware/application/` (этот каталог) — основное приложение: CAN-мост,
  триггеры, USB CDC, хранение конфигурации во Flash. Новое, написано в этой
  сессии.

## ⚠️ Пинаут — ЗАГЛУШКА, требует подтверждения по схеме

Ни одна принципиальная схема не была предоставлена. Все ножки ниже — это
**инженерное предположение** для черновой сборки/симуляции логики, а не
факт реального устройства. Список полностью совпадает с `Inc/main.h`:

## Реализовано по разделам ТЗ

- **ТЗ 10.2–10.3 (UI триггеров, «Настройка»):** сама прошивка не содержит UI
  (он на ПК в `ui/`); прошивка предоставляет TLV-команды
  `CMD_TRIGGER_READ/WRITE/ENABLE` и `CMD_CFG_READ/WRITE/FACTORY_RESET`
  (см. `firmware/PROTOCOL.md` Часть 2), достаточные для реализации кнопок
  «Настроить»/«Записать»/«Заводские настройки» на стороне ПК. **Обработчики
  этих команд на стороне ПК ещё не существуют — это отдельная задача.**
- **ТЗ 11 (конфигуратор, on-demand чтение):** конфигурация читается только
  по явному запросу `CMD_CFG_READ`, автоматического чтения при подключении
  нет — реализовано в `protocol.c`/`device_config.c`.
- **ТЗ 11.2–11.3 (запись имени/serial/VID/PID, переподключение):**
  `CMD_CFG_WRITE` пишет во Flash-страницу конфигурации (`device_config.c`)
  и вызывает программный сброс USB (полный `NVIC_SystemReset()`), после
  чего устройство заново перечисляется с новым именем/serial
  (`usbd_desc.c` читает их из `DeviceConfig_Get()`).
  **Важное упрощение:** ТЗ 11 описывает запись имени/serial как часть
  единого DFU-flashing workflow (патч в «область страницы А» + DFU-загрузка
  нового образа). Здесь реализован более простой путь — прямая запись в
  отдельную Flash-страницу конфигурации *без* перепрошивки кода приложения,
  что при простой смене имени/serial работает эквивалентно и не требует
  повторной заливки `.bin`. Если ТЗ имеет в виду именно патч бинарника перед
  DFU-заливкой (а не отдельную страницу) — это осознанное расхождение,
  см. также обсуждение терминологии «страница А» в `PROTOCOL.md` Часть 3.
- **ТЗ 12.1 (USB throughput ≥1 Мбит/с, 0 потерь CAN при 100% загрузке двух
  шин ~14000 пак/с):** не измерено (нет железа/компилятора в этой сессии).
  Архитектурно приём CAN вынесен в IRQ (`HAL_CAN_RxFifo0MsgPendingCallback`
  в `can_bridge.c`, минимальная работа — копирование в кольцевой буфер), а
  вся тяжёлая логика (парсинг USB-потока, триггеры, пересылка на ПК)
  выполняется в главном цикле — приём CAN физически не может быть
  заблокирован USB/триггерами. Фактическая пропускная способность зависит
  от реализации `usbd_cdc_if.c`/USB-стека ST, который не менялся принципиально
  относительно бутлоадера — числа надо подтверждать осциллографом/логическим
  анализатором на реальной плате.
- **ТЗ 12.2 (кольцевые буферы ≥512 пакетов/канал, drop-oldest + флаг
  ошибки):** `CAN_RING_DEPTH = 1024` (вдвое больше минимума) в
  `can_bridge.c`; переполнение — вытеснение самого старого элемента,
  флаг фиксируется в `CanBridge_TookOverflow()`. **Не подключено к
  протоколу:** сейчас `CanBridge_TookOverflow()` нигде не вызывается из
  `protocol.c` — ПК не узнает о переполнении. Нужно добавить это в
  сообщение об ошибке (в текущем протоколе нет отдельного кода ошибки для
  этого случая — потребует ещё одного расширения Части 2 PROTOCOL.md).
- **ТЗ 12.3 (задержка триггера ≤±1мс, приём не должен блокироваться
  обработкой триггеров):** приём никогда не блокируется — см. выше.
  Задержка ответа реализована через `HAL_GetTick()` (мс-разрешение,
  SysTick) в `trigger.c::Trigger_Poll()`. **Известное ограничение:**
  `HAL_GetTick()` имеет разрешение ровно 1 мс, что находится на границе
  требования ±1мс — джиттер планирования может доходить почти до полного
  тика. Если требование жёсткое, нужно заменить на аппаратный таймер (TIM)
  с прерыванием по совпадению (`stm32f1xx_hal_tim.c`/`_tim_ex.c` уже
  подключены в `Makefile` заранее, но код планирования на TIM ещё не
  написан — сделано намеренно как задел, не как реализация).
- **ТЗ 12.4 (VBUS=0 → автономный CAN+триггеры, USB деактивирован):**
  реализовано в `main.c` — `VBUS_Present()` читает PA9, USB-стек
  запускается/останавливается динамически (`USBD_Start/Stop/DeInit`) по
  изменению VBUS; в автономном режиме CAN и триггеры продолжают работать
  (`Trigger_OnFrame()` вызывается из отдельной ветки главного цикла, минуя
  `Protocol_Poll()`).
- **ТЗ 12.5 (IWDG ~1с):** реализовано в `main.c::MX_IWDG_Init()`,
  `Prescaler=32`, `Reload=1249` (≈1.0с от ~40кГц LSI), `HAL_IWDG_Refresh()`
  вызывается каждую итерацию главного цикла.
- **ТЗ 13 (только SWD, PA15/JTDI → GPIO OUT4, JTAG отключён):** реализовано
  в `main.c::JTAG_Disable_SWD_Only()` через `__HAL_AFIO_REMAP_SWJ_NOJTAG()`,
  вызывается до `MX_GPIO_Init()` (важен порядок — иначе PA15 останется в
  режиме JTDI и не будет работать как обычный GPIO).

## Известные допущения и ограничения (свод)

1. **Пинаут — заглушка**, см. таблицу выше. Единственный источник — текст
   ТЗ, без схемы.
2. **CMD_AUTO_SPEED (0xA0) не делает реального автоопределения скорости.**
   Без платы невозможно безопасно откалибровать переключение
   Normal/Silent TJA1050 и время устаканивания шины. Текущая реализация
   в `protocol.c` возвращает *текущую сконфигурированную* скорость вместо
   результата перебора — временная заглушка, откомментирована в коде.
   См. также `firmware/FIRMWARE_INPUT_REQUEST.md` (раздел про параметры
   автоопределения) — эти параметры так и не были предоставлены.
3. **±1мс задержка триггера не гарантирована аппаратно** — сейчас это
   мс-разрешение `HAL_GetTick()`, см. выше.
4. **Запись Flash блокирует главный цикл на время стирания страницы**
   (десятки мс) — приём CAN в это время буферизуется в кольцевые буферы
   (не в IRQ, там всё быстро), но при экстремальной длительной записи и
   одновременной 100%-загрузке шины возможно исчерпание буфера. См. расчёт
   в `PROTOCOL.md` Часть 3 (конец файла).
5. **`CanBridge_TookOverflow()` пока не отображается отдельным полем в ПК** —
   текущий диагностический C6 сообщает ошибки CAN/bus-off, а счётчик потерь
   кадров требует отдельного расширения payload и теста совместимости.
6. **Термин «страница А»** трактуется как отдельная 2КБ-страница Flash под
   конфигурацию устройства (не как патч в тело прошивки перед DFU-заливкой)
   — см. расхождение в разделе ТЗ 11 выше.
7. **Сборка проверена локально.** `firmware/application` собирается через
   `make` установленным `arm-none-eabi-gcc`; перед выпуском всё равно нужно
   проверить образ на реальной плате и устранить предупреждения toolchain.
8. **Раздел 8 ТЗ (точные поля триггера) не был предоставлен** — формат
   `trigger_t` в `trigger.h` выведен из существующей логики
   `ui/can_trigger_tab.py` на ПК (ID+маска, DLC, данные+маска данных, канал,
   ответный кадр, задержка, вкл/выкл). Если реальный раздел 8 появится —
   сверить и при необходимости изменить структуру (потребует также правки
   `PROTOCOL.md` Части 2.4/2.5 и версии протокола, так как изменение layout
   `trigger_t` несовместимо со старыми сохранёнными данными во Flash).
9. **CRC-8 реализован дважды** (`device_config.c` и `trigger.c`, идентичный
   код) — минорный дубль, можно вынести в общий модуль при рефакторинге,
   не блокирует функциональность.
10. **`CDC_Transmit_FS()` ждёт свободный TX ограниченное число итераций**
   (guard-счётчик в `usbd_cdc_if.c`, ~50000 итераций), после чего отдаёт
   ошибку вместо бесконечного `while()`. Порог не откалиброван по времени
   (зависит от тактовой частоты компилятора/оптимизаций) — при реальном
   тестировании стоит заменить на `HAL_GetTick()`-таймаут в миллисекундах
   для предсказуемости.

## Найдено и исправлено при верификации (без компилятора, только чтением кода)

Из-за отсутствия `arm-none-eabi-gcc` в песочнице верификация делалась
перекрёстным чтением `protocol.c` против `core/can_protocol.py` и
`PROTOCOL.md`. Найдены и исправлены три связанные ошибки в исходной версии
`protocol.c` (все — в разборе/сборке CAN-кадров, не в TLV-командах 0xC0+):

- **Переполнение стекового буфера.** `frame_bytes[13]`/`buf[13]` были
  меньше реального худшего случая (extended, dlc=8 → 16 байт) — исправлено
  на `[16]` в обоих местах.
- **Ошибка на 1 байт в расчёте длины кадра** (`header_len` считался как
  8/6 вместо правильных 7/5 байт до поля `dlc`), из-за чего `total_len`
  получался на 1 байт больше нужного — исправлено.
- **Контрольная сумма считалась без байта маркера**, а в реальном
  `core/can_protocol.py::pack_can_frame/unpack_can_frame` маркер **входит**
  в XOR-сумму. Из-за этого пересылка CAN-кадров в обе стороны никогда не
  прошла бы проверку checksum на реальном ПК-приложении — исправлено и в
  `protocol.c`, и в описании в `PROTOCOL.md` (там тоже была эта ошибка).
- Дополнительно исправлен разбор строки `REBOOT_TO_BOOTLOADER`: если она
  приходила двумя разными USB-пакетами (что штатно возможно), код мог
  потерять первый байт и никогда не распознать magic-строку целиком —
  теперь код ждёт остаток вместо немедленного resync.
- **Более серьёзная находка — арифметическая ошибка в карте Flash.**
  `STM32F105RCTx_APP.ld` указывал `LENGTH = 222K` для секции `FLASH`
  приложения, но реальный зазор до страницы конфигурации
  (`0x0803D800 - 0x08008000`) равен 214 KB, а не 222 KB. При старом
  значении линкер имел право разместить код/данные приложения на 8 KB
  дальше настоящей границы — то есть **внутри** страницы конфигурации,
  которую `CMD_CFG_WRITE`/`CMD_TRIGGER_WRITE` стирают целиком при каждой
  записи. Это могло бы привести к порче работающего кода приложения первой
  же записью настроек через конфигуратор. Исправлено на 214K и в `.ld`,
  и в `PROTOCOL.md` (там же была согласованная, но неверная, таблица
  номеров страниц).

Это не отменяет пункт 7 (код всё ещё не собирался компилятором) — но эти
конкретные баги были найдены логическим сопоставлением с рабочим Python-кодом
и являются высокой уверенности исправлениями независимо от компиляции.

## Сборка

Требуется `arm-none-eabi-gcc`; локальная сборка проверена командой `make`.
На macOS, например: `brew install --cask gcc-arm-embedded` или
`brew install arm-none-eabi-gcc`, ожидаемый путь — `/opt/homebrew/bin/`
(см. также `firmware/bootloader/README.md`, если там описан использовавшийся
путь тулчейна для бутлоадера).

```sh
cd firmware/application
make            # соберёт build/codemaster_app.elf/.bin/.hex
make clean
```

Зависит от `../libs/STM32CubeF1` (уже вендорено в репозитории, используется
общее с бутлоадером дерево HAL/USB-библиотек).

## Прошивка

Два независимых образа на два разных адреса:

- Бутлоадер: `0x08000000` (обычно прошивается один раз через ST-Link/SWD,
  дальше не трогается).
- Приложение: `0x08008000` — либо через SWD (тем же ST-Link), либо через
  сам бутлоадер по USB DFU (см. `firmware/bootloader/README.md` за
  протоколом AN3155, который не менялся).

## Контрольный список перед прошивкой реального устройства

1. Свериться с реальной схемой и поправить весь пинаут в `Inc/main.h`.
2. Собрать (`make`) и устранить все предупреждения/ошибки компилятора; текущая
   локальная сборка проходит, но образ ещё требует проверки на реальной плате.
3. Откалибровать `CAN_TRANSCEIVER_SWITCH_DELAY_US` осциллографом под
   реальный TJA1050/плату.
4. Замерить реальную пропускную способность USB CDC при 100% загрузке
   обеих шин CAN на 500 кбит/с (ТЗ 12.1) — при недостаче рассмотреть
   увеличение `CAN_RING_DEPTH` или оптимизацию `Protocol_Poll()`.
5. Замерить реальный джиттер задержки триггера; при необходимости
   переписать `Trigger_Poll()` на TIM-прерывание вместо `HAL_GetTick()`.
6. Обработка `CMD_CFG_READ/WRITE` добавлена на стороне ПК для быстрой записи
   и чтения конфигурации без перепрошивки приложения. Команды `CMD_TRIGGER_*`
   всё ещё требуют отдельной интеграции с UI.
7. Подключить `CanBridge_TookOverflow()` к протоколу (потребует расширения
   `PROTOCOL.md`).
8. Если появится реальный раздел 8 ТЗ (поля триггера) или «Приложение А» —
   свериться и при расхождениях обновить `trigger_t`/`PROTOCOL.md`.
