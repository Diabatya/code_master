# Протокол обмена ПК ↔ устройство («Приложение А»)

**Статус:** формализовано на основе фактического поведения существующего ПК-кода
(`core/can_protocol.py`, `core/serial_manager.py`, `core/bootloader.py`), так как
отдельного документа «Приложение А» к ТЗ на момент разработки прошивки предоставлено
не было (подтверждено пользователем: «Есть только текст ТЗ, схемы нет»). Часть 1
(кадры CAN, команды 0x90–0xA1) — это **не новый протокол**, а точное описание уже
работающего кода; менять её нельзя, не сломав совместимость с текущим ПК-приложением.
Часть 2 (0xC0–0xCF) — **новые команды**, необходимые для функций из ТЗ (чтение/запись
конфигурации, триггеры, заводской сброс), которых в текущем ПК-коде ещё нет — при
реализации ответной части в PySide6-приложении нужно будет добавить обработчики по
этой же схеме.

Транспорт в обоих случаях — один поток байт USB CDC-ACM (виртуальный COM-порт),
115200/8E1 или произвольные согласно `LineCoding` (реальный битрейт не используется
USB CDC на уровне физики, но должен приниматься без ошибок). Кадры CAN и
команды/ответы могут перемежаться в потоке в любом порядке — устройство обязано
разбирать поток как последовательность независимо начинающихся структур по
однобайтовым маркерам, начиная каждую попытку разбора с поиска ближайшего известного
маркера (см. `core/can_protocol.py::_find_marker`). Приём CAN-кадров имеет приоритет
над отправкой ответов на команды — команда может отработать на один цикл main-loop
позже, если в этот момент шёл приём/пересылка кадра, но кадр CAN никогда не должен
быть отброшен ради обработки команды.

## Часть 1 — существующий протокол (не менять)

### 1.1 Кадры CAN (в обе стороны, ПК→устройство = отправка, устройство→ПК = приём)

Маркеры (см. `core/can_protocol.py`):

| Маркер | Значение |
|---|---|
| `0xBB` | ПК → устройство, стандартный ID (11 бит) |
| `0xBC` | ПК → устройство, расширенный ID (29 бит) |
| `0xAA` | устройство → ПК, стандартный ID (11 бит) |
| `0xAB` | устройство → ПК, расширенный ID (29 бит) |

Формат кадра (все данные — little-endian):

```
[marker:1][channel:1][id:2 или 4][len:1][data:len][checksum:1]
```

- `channel`: `1` = CAN1, `2` = CAN2 (wire-формат, совпадает с `core/can_protocol.py` и UI).
- `id`: 2 байта LE для стандартного маркера (0xBB/0xAA), 4 байта LE для расширенного
  (0xBC/0xAB).
- `len`: 0–8 (CAN 2.0, **не CAN FD** — FD-поддержка была реализована и полностью
  удалена в ПК-коде 14.07.2026, см. `PROJECT_STATUS.md` п.18; прошивка не должна
  предполагать DLC > 8).
- `data`: ровно `len` байт полезной нагрузки.
- `checksum`: XOR всех байт кадра **включая** маркер и **до** самого checksum
  (то есть `marker` тоже входит в сумму) — см. `pack_can_frame()`/`unpack_can_frame()`
  в `can_protocol.py`: там `frame` формируется начиная с байта маркера, и
  `xor_checksum(frame)` считается по этому байтовому массиву целиком, уже
  включающему маркер, перед добавлением самого байта checksum в конец. (Более
  ранняя версия этого файла ошибочно исключала маркер из суммы — исправлено;
  соответствующая ошибка была и в `protocol.c`, тоже исправлена.) Кадр с
  неверной контрольной суммой должен быть отброшен целиком (не считаться началом
  следующего кадра), приёмник продолжает поиск маркера с байта после `marker`.

Длина кадра целиком:
- стандартный: `1 + 1 + 2 + 1 + len + 1 = 6 + len` байт
- расширенный: `1 + 1 + 4 + 1 + len + 1 = 8 + len` байт

Устройство обязано отправлять кадр целиком одной непрерывной последовательностью
байт в CDC IN endpoint (можно несколькими USB-пакетами по 64 байта, но без
посторонних байт между ними).

**TX-эхо.** Поток устройство→ПК включает не только кадры с шины: bxCAN в
Normal-режиме не принимает собственные передачи, поэтому прошивка возвращает
каждый успешно отправленный кадр (ответ триггера, отправленный ПК кадр
0xBB/0xBC) в приёмный поток. Это нужно для цепочек триггеров («триггер B
реагирует на кадр, отправленный триггером A или ПК») и чтобы монитор видел
исходящий трафик — как у внешних анализаторов.

Эхо-кадр помечается в wire-формате: **бит 7 байта `channel` = 1** означает
«внутренняя передача МК» (TX), младшие 7 бит — номер канала 1/2. ПК читает
`channel = byte & 0x7F`, `tx_echo = byte & 0x80` (см. `unpack_can_frame`):
RX-строки — внешний приём с шины, TX-строки — отправлено самим МК; монитор
подсвечивает TX зелёным, в CSV/трейсах пишется колонка `dir`/`DIR=RX|TX`.
Глубина цепочки ограничена `CAN_TX_ECHO_MAX` (8) — два триггера, настроенные
друг на друга, не уйдут в бесконечный пинг-понг. Старая прошивка бит 7 не
ставит — все кадры считаются приёмом (RX).

### 1.2 Команда CMD_DEVICE_ID (идентификация типа устройства)

Запрос (ПК→устройство), один байт:
```
0x90
```

Ответ (устройство→ПК), 3 байта:
```
[0x91][device_type:1][device_version:1]
```

`device_type` — см. `DEVICE_TYPE_*` в `can_protocol.py`:

| Значение | Тип |
|---|---|
| `0x00` | BASIC (базовый, 2×CAN 2.0) |
| `0x01` | ANALOG |
| `0x02` | CAN_FD (зарезервировано, **не используется** — FD снят из ПК-кода) |

Для данного изделия использовать `device_type = 0x00` (BASIC), если пользователь не
укажет иное. `device_version` — однобайтовая версия прошивки устройства (например,
`0x01` = v0.1), инкрементируется вручную при релизах.

### 1.3 Команда CMD_DEVICE_INFO (серийный номер, объём Flash)

Запрос:
```
0x92
```

Ответ:
```
[0x93][serial_len:1][serial: serial_len байт][device_type:1][memory_kb:1]
```

- `serial_len` — длина строки серийного номера в байтах (ASCII, без завершающего
  нуля), максимум по ТЗ 11.2 — **10 символов**.
- `serial` — сам серийный номер как сохранён в конфигурации Flash (см. Часть 3).
- `device_type` — как в 1.2.
- `memory_kb` — объём Flash в килобайтах **одним байтом** (максимум 255). Для
  STM32F105RCT6 (256 KB) это уже **не помещается** в один байт корректно (256 > 255).
  Это ограничение унаследовано от текущего ПК-протокола и не может быть расширено
  без изменения `core/serial_manager.py`. **Решение для прошивки:** отдавать
  `memory_kb = 255` (насыщение), не `256 & 0xFF = 0`, чтобы не давать ложно малое
  значение — задокументировано как известное ограничение протокола, а не баг
  прошивки.

### 1.4 Команда CMD_AUTO_SPEED (автоопределение скорости CAN)

Запрос:
```
0xA0
```

Ответ:
```
[0xA1][speed_hi:1][speed_lo:1]
```

`speed = (speed_hi << 8) | speed_lo`, значение в кбит/с (например, `500` для
500 кбит/с). Устройство определяет скорость перебором стандартных значений
(1000/500/250/125/100/50/20/10 кбит/с) с попыткой синхронизации на шине; при
неудаче на всех значениях возвращает `speed = 0`.

### 1.5 Вход в bootloader (magic-строка)

Приложение обязано отслеживать во входящем CDC-потоке байтовую строку:
```
"\x00REBOOT_TO_BOOTLOADER\n"
```//22 байта, см. `REBOOT_TO_BOOTLOADER_MAGIC` в `core/bootloader.py`

При обнаружении этой точной последовательности (может встретиться в любом месте
потока, не обязательно с начала пакета) устройство должно:
1. записать `0xBEEF` в backup-регистр `BKP->DR1` (переживает system reset,
   очищается при реальном снятии питания);
2. для совместимости со старыми bootloader'ами — также записать `0xDEADBEEF`
   по адресу `0x20004FF0` (legacy: адрес попадает внутрь CAN-буфера
   приложения, поэтому новые bootloader'ы на него не полагаются);
3. вызвать `NVIC_SystemReset()`.

Бутлоадер (уже реализован, `firmware/bootloader/Src/bootloader.c`) при следующем
старте проверит `RCC->CSR & RCC_CSR_SFTRSTF` совместно с `BKP->DR1 == 0xBEEF` и
останется в режиме бутлоадера вместо перехода к приложению.

## Часть 2 — новые команды (для функций из ТЗ 8/10/11, требуют реализации и на ПК)

Все новые команды используют маркер запроса в диапазоне `0xC0–0xC9`, ответы —
`0xD0–0xD9` (диапазон намеренно выбран далеко от занятого 0x90–0xA1, чтобы не
конфликтовать при случайном совпадении байта данных с маркером во время поиска
`_find_marker`). Общий формат запроса/ответа — TLV с явной длиной, чтобы разбор
не зависел от знания структуры при последующем расширении:

```
запрос:  [cmd:1][payload_len:1][payload: payload_len байт]
ответ:   [cmd|0x10:1][status:1][payload_len:1][payload: payload_len байт]
```

`status`: `0x00` = OK, `0x01` = неверный параметр, `0x02` = не удалось записать
Flash, `0x03` = неизвестная команда/версия протокола.

### 2.1 CMD_CFG_READ (0xC0) — чтение конфигурации устройства

Запрос: `[0xC0][0x00]` (без payload).

Ответ: `[0xD0][status][len][device_name_len:1][device_name][serial_len:1][serial][vid:2 LE][pid:2 LE]`

Соответствует ТЗ 11.2: Device Name ≤9 символов, Serial Number ≤10 символов,
опциональные VID/PID (0x0000 = «не задано», использовать `VID=0x0483`,
`PID=0x5740` по умолчанию — см. `firmware/bootloader/README.md`, схема VID/PID).

### 2.2 CMD_CFG_WRITE (0xC1) — запись конфигурации (аналог «Настроить» в ТЗ 10.3)

Запрос: `[0xC1][len][device_name_len][device_name][serial_len][serial][vid:2 LE][pid:2 LE][0xA5][0x5A]`

Ответ: `[0xD1][status][0x00]`. При успехе — запись в Flash (см. Часть 3) и
**программный сброс USB-переподключения** (устройство обязано заново
перечислиться с новым именем/serial — как и штатный процесс прошивки по ТЗ 11.3,
но без стирания и перезаписи всего образа приложения).

Двухбайтовый трейлер `A5 5A` обязателен с версии протокола 3: без него
команда отвергается (`status=0x01`). Это защита от фантомной записи —
мусорный байт `0xC1` при рассинхроне CDC-потока (парсер пересматривает
байты после битого кадра) раньше переписывал имя/серийник и сбрасывал МК.
Прошивка ≤v2 лишние байты в конце payload игнорирует — новый хост с ней
совместим; старый хост на прошивке v3 получает отказ и уходит на запись
конфигурации через DFU.

### 2.3 CMD_CFG_FACTORY_RESET (0xC2) — заводские настройки (ТЗ 10.3 «Заводские настройки»)

Запрос: `[0xC2][0x04]["FCLR"]` — ASCII-ключ обязателен с версии протокола 3
(ранее payload игнорировался, и одиночный мусорный `0xC2` с любым байтом
длины исполнялся как настоящая команда — стирал все триггеры и сбрасывал
МК; воспроизведён в полевом логе: `сброс=0x14`, 0 триггеров после
переподключения). Ответ: `[0xD2][status][0x00]`. Стирает хранилище
триггеров (`Trigger_ClearAll`) и перезагружает устройство. Страница
конфигурации (имя устройства, серийный номер, VID/PID) **не** стирается:
идентичность задаётся при программировании и не является настройкой
оператора. Пользовательские настройки сбрасывает сторона ПК
(`Config.reset_to_defaults` с сохранением ключей идентичности).

### 2.4 CMD_TRIGGER_READ (0xC3) — чтение одного триггера

Запрос: `[0xC3][0x01][index:1]` (`index` 0–48).

Ответ: `[0xD3][status][len][trigger_payload]` — формат `trigger_payload` см. Часть 3
(структура `trigger_t`). Если ТЗ 8 (поля триггера) станет доступен, формат следует
свести к нему 1-в-1; сейчас payload содержит суперсет разумных полей (условие
приёма ID+маска+данные+маска данных+канал, ответ ID+данные+канал+задержка,
включён/выключен), достаточных для реализации логики, аналогичной уже работающей
на ПК `ui/can_trigger_tab.py`.

### 2.5 CMD_TRIGGER_WRITE (0xC4) — запись одного триггера

Запрос: `[0xC4][len][index:1][trigger_payload]`. Ответ: `[0xD4][status][0x00]`.

### 2.6 CMD_TRIGGER_ENABLE (0xC5) — включить/выключить триггер без перезаписи

Запрос: `[0xC5][0x02][index:1][enabled:1]`. Ответ: `[0xD5][status][0x00]`.

**Нумерация каналов в `trigger_t`** — 0-based, как индекс комбобокса UI:
`rx_channel`/`tx_channel`/`src_channel`: `0` = CAN1, `1` = CAN2,
`2` = «CAN1 и CAN2» (на приём матчит кадр с любого канала, на ответ шлёт
фрейм в оба канала). Это отличается от wire-нумерации CAN-кадров (1/2) —
`CanBridge` внутри прошивки хранит кадры с 0-based каналом, а конверсия
в wire-формат происходит только при отправке ответа триггера.

**Формат `trigger_t` v3 (90 байт, magic "TRG2")** — см. `Inc/trigger.h`.
Байты 0..80 совпадают с форматом v2; дальше добавлены опции и CRC уехал
на offset 89. Прошивка принимает на запись обе длины: 82 Б (v2, новые
поля = выкл/«слушать эхо») и 90 Б (v3) — старый ПК продолжает писать
триггеры в новую прошивку. Чтение (`CMD_TRIGGER_READ`) всегда отдаёт
90-байтную запись — хост с protocol<4 должен принять более длинный
payload (поля по смещениям v2 совпадают, хвост можно игнорировать).

```text
offset 0   magic (uint32 "TRG2")          offset 47  delay_ms (uint16 LE)
offset 4   enabled (u8)                   offset 49  reserved[2] = ver,size
offset 5   rx_channel (u8)                offset 51  tx_rtr (u8)
offset 6   rx_extended (u8)               offset 52  cache_enabled (u8)
offset 7   rx_id (uint32 LE)              offset 53  src_channel (u8)
offset 11  rx_id_mask (uint32 LE)         offset 54  src_extended (u8)
offset 15  rx_dlc (u8)                    offset 55  src_id (uint32 LE)
offset 16  rx_data[8]                     offset 59  src_dlc (u8)
offset 24  rx_data_mask[8]                offset 60  src_from[8]
offset 32  tx_channel (u8)                offset 68  src_to[8]
offset 33  tx_extended (u8)               offset 76  tx_interval_ms (u16 LE)
offset 34  tx_id (uint32 LE)              offset 78  tx_count (u8)
offset 38  tx_dlc (u8)                    offset 79  rx_rtr (u8)
offset 39  tx_data[8]                     offset 80  group_seq (u8)
                                          offset 81  rx_fire_limit (u16 LE)
                                          offset 83  rx_flags (u8)
                                          offset 84  src_fire_limit (u16 LE)
                                          offset 86  src_flags (u8)
                                          offset 87  pad[2]
                                          offset 89  crc8
```

**Поля формата v3** (у записей v2 — нули, опции выключены):

- `rx_flags`/`src_flags`, бит 0 = `TRIGGER_F_MUTE_ECHO` — «Слушать
  отправляемое» в UI выключено: триггер/кэш не реагирует на кадры,
  отправленные самим МК (TX-эхо). `0` = слушать и внешние, и свои —
  поведение записей v2 сохраняется без миграции значений.
- `rx_fire_limit` — «Кол-во сработок до смены DATA» приёма: триггер
  исполняет N срабатываний на кадрах с неизменным содержимым (отслеживается
  на уровне ID/канала/DLC-фильтра), затем защёлка в ОЗУ глушит его до
  смены Data; новая Data сбрасывает счётчик, и цикл повторяется.
  `0` = выкл. Состояние только в RAM — сбрасывается при коммите/рестарте.
- `src_fire_limit` — то же для захвата кэша: после N подходящих кадров с
  неизменной Data захват останавливается до смены содержимого (кэш
  сохраняет последнее значение).

`rx_rtr` (offset 79, бывший байт `reserved_pad` — размер записи не
изменился): `0` = срабатывать на любой кадр (поведение старых записей),
`1` = только на RTR-запрос (кадр без Data, сравнение по Data пропускается),
`2` = только на кадр с данными. В UI — кнопка «RTR» в строке «Приём».

`group_seq` (offset 80, бывший `reserved_pad`) — метка группы записей
одного многофреймового триггера; прошивка байт не анализирует, просто
хранит и возвращает (opaque для МК, используется только ПК):

- `0` — базовая запись: одиночный триггер или первая строка ответа
  группы;
- `1..127` — начало строки ответа N развёрнутого триггера;
- `0x80|f` (f=1..126) — фрагмент счётчика: `tx_count` суммируется в
  текущую строку (count>255 пишется кусками по 255 отправок).

Многофреймовый триггер (несколько строк «Фреймы ответа», пауза перед
следующим фреймом, count>255) раскладывается в N подряд идущих записей
с общим условием приёма: у каждой свой фрейм ответа и АБСОЛЮТНАЯ
задержка первой отправки в `delay_ms` (повторы — `tx_count`/
`tx_interval_ms`, как у одиночной). Прошивка исполняет записи группы
независимо — у каждой свой слот отложенной отправки. По вычитке ПК
склеивает группу обратно в один блок: пауза между строками =
`delay_ms[k] - (delay_ms[k-1] + (count[k-1]-1)*interval[k-1])`.
Старые записи имеют group_seq=0 — читаются как одиночные триггеры.

**Режим «автоматическая запись DATA в кэш»** (`cache_enabled=1`):
МК постоянно проверяет шину матчером «Откуда читаем» (`src_channel`,
`src_extended`, `src_id` — точное совпадение; каждый из `src_dlc` байт
Data сравнивается побайтно со своим диапазоном `src_from[i]..src_to[i]`;
`src_dlc=0` — без проверки Data). ИНВЕРТИРОВАННЫЙ диапазон
(`src_from[i] > src_to[i]`) — wildcard-байт «X» UI: позиция не участвует
в сравнении, а при захвате в кэш обнуляется — в ответном кадре на её
месте уходит `0x00`. Каждый подошедший кадр перезаписывает кэш слота в
RAM (не во Flash — ресурс стираний страницы ~10k циклов). При кадре,
подошедшем под «Приём» (`rx_*`), отправляется последний закэшированный
кадр на канал `tx_channel` («Куда отправляем») с паузой `delay_ms`,
`tx_count` повторами и паузой `tx_interval_ms` между ними; каждый повтор
шлёт уже свежие данные кэша. Если кэш ещё пуст — отправки нет.

Многострочный кэш (несколько ID-источников у одного триггера)
раскладывается в группу записей с общим `rx_*` и разными `src_*` —
развёртка и `group_seq` те же, что у многофреймового ответа. У каждой
записи свой слот кэша, поэтому один входящий кадр может пополнить
несколько строк сразу, а срабатывание триггера выпускает пакеты всех
строк с их таймингами.

Wildcard «X» в поле приёма (`rx_data`) кодируется `rx_data_mask[i]=0`:
байт не участвует в сравнении. При вычитке ПК показывает такие позиции
как «X».

### 2.7 CMD_CAN_ERROR_STATUS (0xC6) — статус ошибок/bus-off шины CAN

Добавлено при исправлении находки аудита (CURSOR_FIX_PROMPT.md 4.4): раньше
`can_bridge.c` включал только `CAN_IT_RX_FIFO0_MSG_PENDING` — `AutoBusOff`
(см. `configure_bit_timing()`) восстанавливает bxCAN аппаратно сам, но ни
firmware, ни ПК никогда не узнавали, что шина вообще уходила в bus-off или
ловила ошибки (например, из-за плохого/отсутствующего терминатора).

Запрос: `[0xC6][0x01][channel:1]` (`channel`: 1 = CAN1, 2 = CAN2).

Ответ: `[0xD6][status][0x06][had_error:1][had_busoff:1][last_error_code:4 LE]`

- `had_error` — 1, если после предыдущего опроса этого канала произошла хотя бы
  одна ошибка шины (stuff/form/ACK/bit/CRC, error-warning, error-passive или
  bus-off — см. `HAL_CAN_ERROR_*` в `stm32f1xx_hal_can.h`); флаг сбрасывается
  чтением, как и флаг переполнения RX-кольца (`CanBridge_TookOverflow()`).
- `had_busoff` — отдельный «липкий» флаг: 1, если канал хотя бы раз уходил в
  Bus-Off с прошлого опроса (сбрасывается чтением). `AutoBusOff` восстановит
  шину автоматически, но ПК всё равно стоит предупредить пользователя.
- `last_error_code` — сырой битовый код HAL, зафиксированный на момент
  последней ошибки (диагностика; конкретные биты см. `HAL_CAN_ERROR_*`).

ПК должен опрашивать эту команду периодически (например, в фоне вместе с
чтением CAN-кадров) — иначе кратковременные ошибки между опросами будут
потеряны (флаги сбрасываются чтением, история не хранится).

### 2.8 CMD_CAN_STATS (0xC7) — накопительные счётчики CAN

Запрос: `[0xC7][0x01][channel:1]` (`channel`: 0 = CAN1, 1 = CAN2).

Ответ payload длиной 35 байт:

```text
rx_count:      uint32 LE — принятые CAN-кадры
tx_count:      uint32 LE — успешно переданные CAN-кадры
lost_count:    uint32 LE — кадры, отброшенные из-за переполнения RX ring
error_count:   uint32 LE — CAN error interrupts
busoff_count:  uint32 LE — переходы в bus-off
recovery_count:uint32 LE — автоматические восстановления после bus-off
ready:         uint8     — канал инициализирован и готов
baud_kbps:     uint16 LE — фактически применённый бод-рейт канала
tx_fail_count: uint32 LE — кадры, не отправленные: все TX-ящики заняты
                           дольше бюджета ожидания (арбитраж под
                           нагрузкой, шторм ретраев без ACK, bus-off).
                           Именно так выглядит «потерянный» ответ
                           триггера/шлюза — раньше был невидим.

                           из главного цикла (CanBridge_PollHealth).

                           кадров пропустило (на F105 вектор CAN1_RX0
                           делит линию с USB_LP — при USB-шторме доставка
                           может теряться; опрос спасает кадры до

Host должен принимать и старые короткие ответы (12/24/27/31 байт) для
совместимости — недостающие хвостовые поля считать нулевыми.

Счётчики монотонные до перезапуска устройства. Команда их не очищает.

### 2.9 CMD_TRIGGER_STAGE (0xCA) и CMD_TRIGGER_COMMIT (0xCB)

`CMD_TRIGGER_STAGE` принимает `[index:1][trigger_t]` — запись 82 Б (v2)
или 90 Б (v3), проверяет запись и
сохраняет её только в RAM. `CMD_TRIGGER_COMMIT` принимает `[total:1]` —
итоговую длину упакованного списка — и одной операцией перезаписывает
хранилище триггеров во Flash: позиции без staged-записи берутся из текущего
списка, хвост за `total` отбрасывается (так выражается удаление).
Полное стирание списка — `[0x00][0xA5]` (байт-ключ обязателен с версии
протокола 3: голый `[0xCB][0x01][0x00]` отвергается как возможный фантом
рассинхрона). Пустой payload COMMIT — «закоммить staged, сохранив размер» —
с v3 отвергается (`status=0x01`): хост его не использует, а двухбайтовый
`CB 00` — ровно тот фантом, что дописывал staged-записи без ведома ПК.
При ошибке Flash RAM-состояние откатывается к предыдущей копии.

Staged-данные протухают через 15 с после последнего STAGE: оборванная
сессия записи (USB-обрыв между STAGE и COMMIT) не должна оставлять записи
вооружёнными навсегда — иначе любой поздний COMMIT, в т.ч. мусорный байт
`0xCB` из рассинхронизированного потока, дописывал бы их во Flash
«фантомным» триггером, воскресающим после каждого ребута.

**Хранилище триггеров v4** (см. карту Flash в Части 3): пул страниц
`0x0803E000`–`0x0803FFFF` над config-страницей. Активная область привязана
к верху пула и состоит из 16-байтного заголовка "TRGH" (`magic`, `version`,
`count`, `generation`, `crc8`) и идущих следом `count` записей — по 90 байт
в хранилище v4, по 82 байта в хранилище v3 (читается и мигрирует: шаг
записей выбирается по `version` заголовка) — без пропусков. Область растёт вниз от `0x08040000` по мере добавления
триггеров; пустое устройство не занимает ни страницы. При старте прошивка
находит область сканированием заголовков по страницам пула (валидный
magic+CRC, наибольший `generation`) — фиксированного адреса нет, прошивка
может расти без сдвига формата. Записи старого фиксированного региона
v2 (49 слотов с `0x0803E000`) импортируются при первой загрузке и сразу
финализируются записью v3-хранилища в верх пула — легаси-страница при
этом не стирается, чтобы обрыв питания посреди переезда не терял данные:
следующий старт повторит миграцию. Без немедленной финализации легаси
реимпортировалось при каждом старте, и удалённый, но ни разу не
сохранённый триггер воскресал «фантомом» после каждого ребута.

**Атомарность COMMIT**: запись хранилища идёт в два приёма — сначала
записи, заголовок "TRGH" прошивается последним и служит точкой коммита:
область без валидного заголовка для сканирования невидима. Если рядом с
действующим хранилищем есть свободные страницы, новая область пишется на
второй якорь (низ пула, `0x0803E000`), а прежняя стирается уже после
успешной записи — обрыв посреди коммита (IWDG/сброс/питание) оставляет
целым старый список, а не урезанный. Когда оба якоря заняты прежним
хранилищем (большие списки), выполняется полная зачистка пула — обрыв
тогда даёт честное «пусто», а не мусорные частичные записи.

`CMD_TRIGGER_READ` при `index >= count` отвечает статусом `0x01` — так
хост узнаёт реальную длину списка, не перебирая все слоты.

### 2.10 CMD_TRIGGER_STATS (0xC8) — счётчики движка триггеров

Запрос: `[0xC8][0x00]`.

Ответ payload длиной 16 байт:

```text
fired_count:       uint32 LE — успешно отправленные ответы триггеров
max_lateness_ms:   uint32 LE — макс. опоздание отложенной отправки
flash_valid_count: uint8  — включённых триггеров, прочитанных из Flash
                            при старте (0 при сохранённых триггерах =
                            страницы не пережили питание)
config_valid:      uint8  — валидность страницы конфигурации

                            триггера то был, то не был» на нагруженной

```

Host должен принимать и старые короткие ответы (8/12 байт) —
недостающие поля считать нулевыми.

### 2.11 CMD_USB_STATS (0xCC) — потерянные USB CDC TX-передачи

Запрос: `[0xCC][0x00]`.

Ответ payload (базовый): `tx_dropped: uint32 LE`. Счётчик увеличивается
при TX timeout или отказе USB CDC передачи и сохраняется до перезапуска
устройства.

Расширенный ответ (20 байт) добавляет полевую телеметрию «МК медленный

offset 4   tx_busy_waits:  uint32 LE — сколько раз IN-эндпоинт ждал

offset 8   cmd_count:      uint32 LE — команд дошло до обработчика
offset 12  last_cmd_ms:    uint32 LE — мс обработки последней команды
offset 16  poll_count:     uint32 LE — итерации Protocol_Poll (замирает
                             при голодании главного цикла/IRQ-шторме)
```

### 2.12 CMD_SYSTEM_INFO (0xC9) — информация о системе

Запрос: `[0xC9][0x00]`.

Ответ payload: минимум 16 байт (базовая часть), актуальные прошивки — 76 байт:

```text
offset 0  application_version: uint8
offset 1  protocol_version:    uint8
offset 2  flash_size_kb:       uint16 LE
offset 4  config_format:       uint8
offset 5  config_record_length:uint8
offset 6  trigger_count:       uint8
offset 7  config_valid:        uint8
offset 8  application_size:    uint32 LE
offset 12 application_crc32:   uint32 LE
offset 16 mcu_uid96:           12 байт (Unique Device ID, 0x1FFFF7E8)
offset 28 build_datetime:      20 байт ASCII ("Mmm dd yyyy hh:mm:ss")
offset 48 git_commit:          8 байт ASCII (короткий hash, с нулями)
offset 56 reset_flags:         uint8 — App_GetResetFlags(), см. main.h
offset 57 usb_reset_count:     uint8 — CDC_GetUsbResetCount() (насыщается на 255)
offset 58 usb_disconnect_count:uint8 — CDC_GetUsbDisconnectCount() (насыщается на 255)
offset 59 fault_code:          uint8 — App_GetFaultCode(), !=0 — краш перед последним сбросом
offset 60 rx_overflow_bytes:   uint32 LE — CDC_GetRxOverflowCount()
offset 64 stack_free_bytes:    uint32 LE — App_GetStackFreeBytes(): худший
                                зафиксированный запас между концом .bss и
                                пиком использования стека с момента старта
                                (аудит: два CAN-кольца съедают ~35 КБ из
                                64 КБ RAM, стек+куча делят оставшиеся ~5 КБ
                                с прерываниями — см. main.c)
offset 68 fault_pc:            uint32 LE — застеканный PC последнего фолта
                                (BKP->DR4/DR5, fault_capture в
                                stm32f1xx_it.c) — точный адрес инструкции
                                краха; 0 — фолта не было
offset 72 fault_cfsr:          uint32 LE — SCB->CFSR на момент фолта
                                (BKP->DR6/DR7): класс — precise/imprecise
                                bus, unalign, invstate и т.д.
```

Читатель обязан проверять длину payload: старые прошивки отвечают
ровно 16 байтами и не содержат полей после offset 15; поля из хвоста
[56..67] проверяются по длине ответа индивидуально (см.
`SerialManager.read_system_info()`), т.к. добавлялись постепенно.

`protocol_version` (offset 1): `1` — базовый набор команд 0xC0–0xCD;
`2` — добавлен `CMD_CAN_SPEED` (0xCE); `3` — ключи деструктивных команд
(`CMD_CFG_WRITE`/`CMD_CFG_FACTORY_RESET`/`CMD_TRIGGER_COMMIT` требуют
байт-ключ в payload); `4` — записи триггеров v3, 90 байт (`fire_limit`
и флаги эха; старым прошивкам хост шлёт 82 Б); `5` — имена триггеров
(`CMD_TRIGGER_NAME_*`, 0xD0–0xD2) в config-странице.

### 2.13 CMD_CAN_SPEED (0xCE) — установка бод-рейта CAN-канала

Запрос: `[0xCE][0x03][channel][baud_kbps LE u16]`.

- `channel`: `1` = CAN1, `2` = CAN2 — каналы независимы.
- `baud_kbps`: бод-рейт в кбит/с. Поддерживаются только значения из
  таблицы бит-тайминга bxCAN при APB1 = 36 МГц: `1000, 500, 250, 125,
  100, 50, 20, 10` (`configure_bit_timing` в `can_bridge.c`).

Устройство применяет бод-рейт к периферии немедленно
(`CanBridge_SetBaud` — периферия кратко уходит в init mode и возвращается
на шину с новым таймингом; режим трансивера Normal/Silent и терминатор
удерживаются, т.к. они GPIO-управляемые), затем персистит значение в
расширенной записи конфигурационной страницы — скорость сохраняется после
ребута/выключения и используется автономными триггерами/шлюзом.

Ответ payload: `baud_applied: uint16 LE` — фактически применённый бод
(позволяет хосту отобразить реальное состояние канала).

Статусы: `0x00` — применено и сохранено; `0x01` — неверный payload;
`0x02` — бод-рейт не поддерживается или CAN не инициализирован;
`0x03` — применено, но запись во Flash не удалась (до ребута работает,
после — прежнее значение).

### 2.14 CMD_EVENT_LOG (0xCF) — Flash-журнал событий МК

Диагностика полевого симптома «МК теряет связь с ПК, пока не отключишь
один из CAN-проводов»: обычная статистика (CMD_CAN_STATS/CMD_USB_STATS)
показывает только текущее состояние, а этот журнал хранит хронологию —
что происходило на устройстве, в том числе когда ПК его уже не читал.
Хранилище — кольцо на 4 страницах Flash (`0x0803B000..0x0803CFFF`, см.
Часть 3), 16-байтная запись на событие (128/страницу), переживает и
мягкий сброс, и отключение питания. Не поддерживается прошивками с
протоколом версии < вводящей эту команду — старые прошивки отвечают
статусом «неизвестная команда» (`0x03`), хост должен обрабатывать это
как «журнал недоступен», а не как ошибку связи.

Запрос (payload опционален): `[0xCF][len][after_seq: u32 LE][max_count: u8]`.

- `after_seq` — вернуть только записи с `seq > after_seq` (0 = с начала
  журнала). Пустой или укороченный payload трактуется как 0.
- `max_count` — не больше 23 (лимит по размеру ответа); 0 или больше 23
  трактуется как значение по умолчанию (23).

Ответ payload: `[count: u8]` + `count` записей по 11 байт:

```text
offset 0  seq:          uint32 LE — монотонный номер записи
offset 4  timestamp_ms: uint32 LE — HAL_GetTick() в момент записи (аптайм МК)
offset 8  type:         uint8    — см. event_log_type_t ниже
offset 9  channel:      uint8    — смысл зависит от type; 0xFF = не применимо
offset 10 code:         uint8    — смысл зависит от type
```

Постраничное чтение: хост повторяет запрос с `after_seq` = `seq`
последней полученной записи, пока не получит `count < max_count`
(журнал вычитан целиком) — см. `SerialManager.read_full_event_log()`.

`event_log_type_t`:

| type | Событие | channel | code |
|---|---|---|---|
| 1 | Старт МК (boot) | код фолта (`App_GetFaultCode`: 0=нет, 1=HardFault, 2=MemManage, 3=BusFault, 4=UsageFault) | причина сброса, биты RCC->CSR[31:24]: `0x04`=PIN, `0x08`=POR, `0x10`=soft, `0x20`=IWDG, `0x40`=WWDG, `0x80`=LPWR |
| 2 | Ошибка CAN | 0/1 = CAN1/CAN2 | LEC[2:0] из ESR: 1=Stuff, 2=Form, 3=ACK, 4=Bit recessive, 5=Bit dominant, 6=CRC, 7=software |
| 3 | Bus-off | 0/1 | — |
| 4 | Восстановление после bus-off | 0/1 | — |
| 5 | Переполнение RX-кольца (drop-oldest) | 0/1 | — |
| 6 | Backstop поймал кадр(ы) из FIFO0 (IRQ RX0 пропустил доставку) | 0/1 | — |
| 7 | USB bus reset (реэнумерация) | 0xFF | счётчик `CDC_GetUsbResetCount()` на момент события |
| 8 | USB физический disconnect (SEDET/просадка VBUS) | 0xFF | счётчик `CDC_GetUsbDisconnectCount()` |
| 9 | USB TX голодал >100 мс (хост не читает) | 0xFF | — |
| 10 | Переполнение программного RX FIFO (usbd_cdc_if.c, 2 КБ) | 0xFF | байт потеряно с прошлой записи (насыщение на 0xFF) |
| 11 | Вход в загрузчик | 0xFF | 0 — переход по команде ПК (пишет приложение перед сбросом); 1 — бутлоадер остался по флагу хоста (BKP->DR1); 2 — бутлоадер остался: приложение невалидно/отсутствует |

Запись — только из главного цикла (никогда из IRQ), с троттлингом
~500 мс на пару (type, channel): непрерывный шторм ошибок на убитой шине
не должен истощать ресурс стираний Flash за часы вместо лет. Стирание
происходит постранично (128 записей разом) только при первом заходе в
новую страницу кольца — включая первый заход после обновления прошивки,
когда область могла быть занята кодом предыдущего приложения.

`EVLOG_BOOT` пишется настолько рано, насколько позволяет HAL: сразу после
`MX_IWDG_Init()` (стирание страницы при первом заходе требует живого
сторожа), до загрузки конфигурации/триггеров и до CAN/USB. Записи типа 11
с code 1/2 пишет сам бутлоадер (`firmware/bootloader/Src/event_log_bl.c`)
при входе в режим загрузки — по строгому append-only правилу: бутлоадер
никогда не стирает страницы журнала, занятой слот пропускается. Это делает
видимым сеанс прошивки, в т.ч. случай «приложение не прошло проверку —
устройство осталось в загрузчике». Бутлоадеры, прошитые до этой версии,
таких записей не оставляют — журнал это переживает (записей просто нет).

### 2.15 CMD_TRIGGER_NAME_* (0xD0–0xD2) — имена триггеров

Человекочитаемые имена триггеров для отображения в конфигураторе. Имя
НЕ участвует в исполнении триггера и поэтому не хранится в `trigger_t`
(записей до 70, RAM занят CAN-кольцами): это отдельная запись
`trigger_names_t` (394 Б) в config-странице `0x0803D800` по смещению 48,
сразу за `device_ext_config_t`.

- `index` — плоский слот базовой записи группы (`group_seq == 0`) в
  пуле триггеров — тот же индекс, что у `CMD_TRIGGER_READ`. Диапазон:
  `0..23` (`TRIGGER_NAME_MAX`); триггеры глубже работают без имён.
- Имя — UTF-8 без терминатора, до 16 байт (`TRIGGER_NAME_LEN`).

`CMD_TRIGGER_NAME_READ (0xD0)`: запрос `[0xD0][0x01][index]`,
ответ `[len:1][имя]` (`len=0` — имени нет; `status=0x01` — неверный
payload, `index ≥ 24` возвращает пустое имя, а не ошибку).

`CMD_TRIGGER_NAME_WRITE (0xD1)`: запрос `[0xD1][2+len][index][len][имя]`
— кладёт имя только в RAM-зеркало, Flash не трогает. Статусы:
`0x00` — принято; `0x01` — `index ≥ 24`, `len > 16` или обрезанный payload.

`CMD_TRIGGER_NAME_COMMIT (0xD2)`: запрос `[0xD2][0x00]` — одна
перезапись всей config-страницы (main + ext + имена). Статусы:
`0x00` — записано и проверено; `0x02` — программирование/верификация
не удалась. Хост обязан слать COMMIT имен **после** успешного
`CMD_TRIGGER_COMMIT`: индекс имени привязан к слоту в новом пуле.

Отсутствующая/битая запись `trigger_names_t` — «имён нет», остальная
конфигурация не затрагивается. `CMD_CFG_FACTORY_RESET` стирает имена
вместе с остальной конфигурацией. Прошивки с `protocol_version < 5`
отвечают `0x03` (неизвестная команда) — хост трактует это как «функция
недоступна», имена в этом случае живут только в файле конфигурации ПК.

## Часть 3 — формат хранения конфигурации во Flash («страница А»)

В ТЗ 11.2 «область страницы А» означает отдельную страницу конфигурации
устройства, а не последнюю физическую страницу Flash: последние страницы
зарезервированы под триггеры. Не путать её со страницей разделения
бутлоадера/приложения. Используется отдельная страница, не пересекающаяся
с образом кода приложения, чтобы прошивка нового `.bin`/`.hex` не требовала
пересохранения имени/серийника при каждом обновлении (конфигуратор трогает Flash
конфигурации только явно, по ТЗ 11.3).

Карта Flash (STM32F105RCT6, 256 KB, страница = 2048 байт, подтверждено в
`firmware/bootloader/Src/bootloader.c`):

| Адрес | Размер | Назначение |
|---|---|---|
| `0x08000000`–`0x08007FFF` | 32 KB (стр. 0–15) | Бутлоадер (не трогать) |
| `0x08008000`–`0x0803AFFF` | 204 KB (стр. 16–117) | Приложение (код) |
| `0x0803B000`–`0x0803CFFF` | 8 KB (стр. 118–121) | **Журнал событий** (event_log.h) — кольцо 16-байтных записей, 128/страницу, переживает мягкий сброс и отключение питания |
| `0x0803D000`–`0x0803D7FF` | 2 KB (стр. 122) | Метаданные целостности application (CRC32/размер) |
| `0x0803D800`–`0x0803DFFF` | 2 KB (стр. 123) | **Конфигурация устройства**: основная запись (имя/serial/VID/PID, 32 Б), расширенная `device_ext_config_t` (бод-рейты CAN, смещение 32, 16 Б), таблица имён триггеров `trigger_names_t` (смещение 48, 394 Б) |
| `0x0803E000`–`0x0803FFFF` | 8 KB (стр. 124–127) | Пул хранилища триггеров v4: область привязана к ВЕРХУ Flash и растёт вниз — 16-байтный заголовок "TRGH" + упакованный список записей × 90 байт (до 70 — лимит RAM; хранилища v3 с записями 82 Б читаются и мигрируют). Пустое устройство не занимает ни страницы; фиксированного адреса области нет — прошивка находит её сканированием заголовка |

Первые 212 KB после bootloader отданы под код application. Следующая
страница зарезервирована под метаданные целостности: bootloader хранит там
magic, версию, размер образа и CRC32. Конфигурация и триггеры находятся в
отдельных страницах и не должны попадать в linker FLASH region.

Формат страницы метаданных application (`0x0803D000`):

```
offset 0  : uint32_t magic         (0x41505031 = "APP1")
offset 4  : uint16_t version        (1)
offset 6  : uint16_t reserved
offset 8  : uint32_t image_size     (байт от 0x08008000)
offset 12 : uint32_t crc32         (CRC-32/IEEE по image_size байтам)
```

Bootloader проверяет метаданные строго: application запускается только при
валидном magic + совпавшем CRC32. Стёртая страница (0xFF), обнулённый magic
(0x00 — записывается конфигуратором в начале обновления, «UPDATE_STARTED»)
или незаписанная запись означают «обновление не завершено» — устройство
остаётся в bootloader. Метаданные всегда пишутся последним шагом, после
кода и верификации — это «флаг завершённого обновления» («UPDATE_VERIFIED»).

Через AN3155 разрешены запись и постраничное стирание только для
`0x08008000`–`0x0803DFFF` (application + metadata + config). Область
триггеров `0x0803E000`–`0x0803FFFF` через AN3155 недоступна — триггеры
обновляются только командами CMD_TRIGGER_STAGE/COMMIT. Mass erase (0xFFFF)
по-прежнему стирает весь application-регион целиком.

Формат страницы конфигурации (`device_config_t`, см. `Inc/device_config.h`):

```
offset 0   : uint32_t magic         (0x43464730 = "CFG0")
offset 4   : uint8_t  device_name_len
offset 5   : char     device_name[9]
offset 14  : uint8_t  serial_len
offset 15  : char     serial[10]
offset 25  : uint16_t vid
offset 27  : uint16_t pid
offset 29  : uint8_t  format_version (0 = legacy, 1 = current)
offset 30  : uint8_t  record_length  (32 for current format)
offset 31  : uint8_t  crc8          (CRC-8, полином 0x07, по байтам offset 0..30)
```

Всего 32 байта, выровнено под half-word запись HAL (`HAL_FLASH_Program` с
`FLASH_TYPEPROGRAM_HALFWORD`, как в существующем `bootloader.c`). При `magic` или
`crc8` не совпадающих с ожидаемым — конфигурация считается «пустой» (заводское
состояние), используется значение по умолчанию (см. `device_config.c`:
`device_name="CodeMaster"` обрезано до 9 симв. → `"CodeMaste"`, `serial=""`,
`vid=0x0483`, `pid=0x5740`).

### Расширенная запись (`device_ext_config_t`, offset 32 той же страницы)

Настройки, добавленные после выпуска устройств, лежат отдельной записью
сразу за основной — основной 32-байтный формат остаётся байт-совместимым
со старыми версиями. Записывается тем же проходом `flash_write_config`,
что и основная, поэтому CMD_CFG_WRITE её не сбрасывает. Невалидная или
отсутствующая запись (стёртая страница старых прошивок) = значения по
умолчанию, валидность основной записи она не ломает.

```
offset 32+0   : uint32_t magic           (0x43455830 = "CEX0")
offset 32+4   : uint16_t can1_baud_kbps  (по умолчанию 500)
offset 32+6   : uint16_t can2_baud_kbps  (по умолчанию 500)
offset 32+8   : uint8_t  version         (1)
offset 32+9   : uint8_t  reserved[6]
offset 32+15  : uint8_t  crc8            (CRC-8, полином 0x07, offset 32+0..14)
```

CAN-бод-рейты хранятся на устройстве, потому что приём/передача/триггеры/
шлюз работают автономно (ТЗ 12.4): выставленные оператором 250 кбит/с
должны держаться и после отключения ПК и после цикла питания. Заводской
сброс возвращает обе скорости к 500 кбит/с.

**Важно (эксплуатационное ограничение, зафиксировать как допущение):** запись
одной страницы Flash требует предварительного стирания всей страницы (2 KB), что
занимает единицы–десятки миллисекунд — на это время прерывания HAL Flash
блокируют весь main-loop (это ограничение периферии, не прошивки). Поэтому
CMD_CFG_WRITE/CMD_TRIGGER_WRITE не должны вызываться на устройстве, когда идёт
активная передача CAN на 100% загрузке шины — приём в это время будет
буферизован в кольцевые буферы CAN (см. Часть 4 в README) и не потеряется при
разумной длительности стирания (≤20 мс на страницу при 512-глубоких буферах и
14000 пак/с это ~7 кадров запаса на канал, что укладывается в буфер, но близко
к пределу — задокументировано как риск в README).
