# Протокол обмена ПК ↔ устройство («Приложение А»)

**Статус:** формализовано на основе фактического поведения существующего ПК-кода
(`core/can_protocol.py`, `core/serial_manager.py`, `core/bootloader.py`), так как
отдельного документа «Приложение А» к ТЗ на момент разработки прошивки предоставлено
не было (подтверждено пользователем: «Есть только текст ТЗ, схемы нет»). Часть 1
(кадры CAN, команды 0x90–0xA1) — это **не новый протокол**, а точное описание уже
работающего кода; менять её нельзя, не сломав совместимость с текущим ПК-приложением.
Часть 2 (0xC0–0xCF) — **новые команды**, необходимые для функций из ТЗ (чтение/запись
конфигурации, триггеры, заводской сброс), которых в текущем ПК-коде ещё нет — при
реализации ответной части в PySide6-приложении нужно будет добавить обработчики по
этой же схеме.

Транспорт в обоих случаях — один поток байт USB CDC-ACM (виртуальный COM-порт),
115200/8E1 или произвольные согласно `LineCoding` (реальный битрейт не используется
USB CDC на уровне физики, но должен приниматься без ошибок). Кадры CAN и
команды/ответы могут перемежаться в потоке в любом порядке — устройство обязано
разбирать поток как последовательность независимо начинающихся структур по
однобайтовым маркерам, начиная каждую попытку разбора с поиска ближайшего известного
маркера (см. `core/can_protocol.py::_find_marker`). Приём CAN-кадров имеет приоритет
над отправкой ответов на команды — команда может отработать на один цикл main-loop
позже, если в этот момент шёл приём/пересылка кадра, но кадр CAN никогда не должен
быть отброшен ради обработки команды.

## Часть 1 — существующий протокол (не менять)

### 1.1 Кадры CAN (в обе стороны, ПК→устройство = отправка, устройство→ПК = приём)

Маркеры (см. `core/can_protocol.py`):

| Маркер | Значение |
|---|---|
| `0xBB` | ПК → устройство, стандартный ID (11 бит) |
| `0xBC` | ПК → устройство, расширенный ID (29 бит) |
| `0xAA` | устройство → ПК, стандартный ID (11 бит) |
| `0xAB` | устройство → ПК, расширенный ID (29 бит) |

Формат кадра (все данные — little-endian):

```
[marker:1][channel:1][id:2 или 4][len:1][data:len][checksum:1]
```

- `channel`: `1` = CAN1, `2` = CAN2 (wire-формат, совпадает с `core/can_protocol.py` и UI).
- `id`: 2 байта LE для стандартного маркера (0xBB/0xAA), 4 байта LE для расширенного
  (0xBC/0xAB).
- `len`: 0–8 (CAN 2.0, **не CAN FD** — FD-поддержка была реализована и полностью
  удалена в ПК-коде 14.07.2026, см. `PROJECT_STATUS.md` п.18; прошивка не должна
  предполагать DLC > 8).
- `data`: ровно `len` байт полезной нагрузки.
- `checksum`: XOR всех байт кадра **включая** маркер и **до** самого checksum
  (то есть `marker` тоже входит в сумму) — см. `pack_can_frame()`/`unpack_can_frame()`
  в `can_protocol.py`: там `frame` формируется начиная с байта маркера, и
  `xor_checksum(frame)` считается по этому байтовому массиву целиком, уже
  включающему маркер, перед добавлением самого байта checksum в конец. (Более
  ранняя версия этого файла ошибочно исключала маркер из суммы — исправлено;
  соответствующая ошибка была и в `protocol.c`, тоже исправлена.) Кадр с
  неверной контрольной суммой должен быть отброшен целиком (не считаться началом
  следующего кадра), приёмник продолжает поиск маркера с байта после `marker`.

Длина кадра целиком:
- стандартный: `1 + 1 + 2 + 1 + len + 1 = 6 + len` байт
- расширенный: `1 + 1 + 4 + 1 + len + 1 = 8 + len` байт

Устройство обязано отправлять кадр целиком одной непрерывной последовательностью
байт в CDC IN endpoint (можно несколькими USB-пакетами по 64 байта, но без
посторонних байт между ними).

### 1.2 Команда CMD_DEVICE_ID (идентификация типа устройства)

Запрос (ПК→устройство), один байт:
```
0x90
```

Ответ (устройство→ПК), 3 байта:
```
[0x91][device_type:1][device_version:1]
```

`device_type` — см. `DEVICE_TYPE_*` в `can_protocol.py`:

| Значение | Тип |
|---|---|
| `0x00` | BASIC (базовый, 2×CAN 2.0) |
| `0x01` | ANALOG |
| `0x02` | CAN_FD (зарезервировано, **не используется** — FD снят из ПК-кода) |

Для данного изделия использовать `device_type = 0x00` (BASIC), если пользователь не
укажет иное. `device_version` — однобайтовая версия прошивки устройства (например,
`0x01` = v0.1), инкрементируется вручную при релизах.

### 1.3 Команда CMD_DEVICE_INFO (серийный номер, объём Flash)

Запрос:
```
0x92
```

Ответ:
```
[0x93][serial_len:1][serial: serial_len байт][device_type:1][memory_kb:1]
```

- `serial_len` — длина строки серийного номера в байтах (ASCII, без завершающего
  нуля), максимум по ТЗ 11.2 — **10 символов**.
- `serial` — сам серийный номер как сохранён в конфигурации Flash (см. Часть 3).
- `device_type` — как в 1.2.
- `memory_kb` — объём Flash в килобайтах **одним байтом** (максимум 255). Для
  STM32F105RCT6 (256 KB) это уже **не помещается** в один байт корректно (256 > 255).
  Это ограничение унаследовано от текущего ПК-протокола и не может быть расширено
  без изменения `core/serial_manager.py`. **Решение для прошивки:** отдавать
  `memory_kb = 255` (насыщение), не `256 & 0xFF = 0`, чтобы не давать ложно малое
  значение — задокументировано как известное ограничение протокола, а не баг
  прошивки.

### 1.4 Команда CMD_AUTO_SPEED (автоопределение скорости CAN)

Запрос:
```
0xA0
```

Ответ:
```
[0xA1][speed_hi:1][speed_lo:1]
```

`speed = (speed_hi << 8) | speed_lo`, значение в кбит/с (например, `500` для
500 кбит/с). Устройство определяет скорость перебором стандартных значений
(1000/500/250/125/100/50/20/10 кбит/с) с попыткой синхронизации на шине; при
неудаче на всех значениях возвращает `speed = 0`.

### 1.5 Вход в bootloader (magic-строка)

Приложение обязано отслеживать во входящем CDC-потоке байтовую строку:
```
"\x00REBOOT_TO_BOOTLOADER\n"
```//22 байта, см. `REBOOT_TO_BOOTLOADER_MAGIC` в `core/bootloader.py`

При обнаружении этой точной последовательности (может встретиться в любом месте
потока, не обязательно с начала пакета) устройство должно:
1. записать `0xDEADBEEF` по адресу `0x20004FF0` (SRAM, вне `.data`/`.bss`);
2. вызвать `NVIC_SystemReset()`.

Бутлоадер (уже реализован, `firmware/bootloader/Src/bootloader.c`) при следующем
старте проверит `RCC->CSR & RCC_CSR_SFTRSTF` совместно с этим magic-значением и
останется в режиме бутлоадера вместо перехода к приложению.

## Часть 2 — новые команды (для функций из ТЗ 8/10/11, требуют реализации и на ПК)

Все новые команды используют маркер запроса в диапазоне `0xC0–0xC9`, ответы —
`0xD0–0xD9` (диапазон намеренно выбран далеко от занятого 0x90–0xA1, чтобы не
конфликтовать при случайном совпадении байта данных с маркером во время поиска
`_find_marker`). Общий формат запроса/ответа — TLV с явной длиной, чтобы разбор
не зависел от знания структуры при последующем расширении:

```
запрос:  [cmd:1][payload_len:1][payload: payload_len байт]
ответ:   [cmd|0x10:1][status:1][payload_len:1][payload: payload_len байт]
```

`status`: `0x00` = OK, `0x01` = неверный параметр, `0x02` = не удалось записать
Flash, `0x03` = неизвестная команда/версия протокола.

### 2.1 CMD_CFG_READ (0xC0) — чтение конфигурации устройства

Запрос: `[0xC0][0x00]` (без payload).

Ответ: `[0xD0][status][len][device_name_len:1][device_name][serial_len:1][serial][vid:2 LE][pid:2 LE]`

Соответствует ТЗ 11.2: Device Name ≤9 символов, Serial Number ≤10 символов,
опциональные VID/PID (0x0000 = «не задано», использовать `VID=0x0483`,
`PID=0x5740` по умолчанию — см. `firmware/bootloader/README.md`, схема VID/PID).

### 2.2 CMD_CFG_WRITE (0xC1) — запись конфигурации (аналог «Настроить» в ТЗ 10.3)

Запрос: `[0xC1][len][device_name_len][device_name][serial_len][serial][vid:2 LE][pid:2 LE]`

Ответ: `[0xD1][status][0x00]`. При успехе — запись в Flash (см. Часть 3) и
**программный сброс USB-переподключения** (устройство обязано заново
перечислиться с новым именем/serial — как и штатный процесс прошивки по ТЗ 11.3,
но без стирания и перезаписи всего образа приложения).

### 2.3 CMD_CFG_FACTORY_RESET (0xC2) — заводские настройки (ТЗ 10.3 «Заводские настройки»)

Запрос: `[0xC2][0x00]`. Ответ: `[0xD2][status][0x00]`. Стирает страницу конфигурации
Flash и восстанавливает значения по умолчанию (см. Часть 3), затем программно
переподключает USB.

### 2.4 CMD_TRIGGER_READ (0xC3) — чтение одного триггера

Запрос: `[0xC3][0x01][index:1]` (`index` 0–9, соответствует вкладкам 1–10 из ТЗ 10.2).

Ответ: `[0xD3][status][len][trigger_payload]` — формат `trigger_payload` см. Часть 3
(структура `trigger_t`). Если ТЗ 8 (поля триггера) станет доступен, формат следует
свести к нему 1-в-1; сейчас payload содержит суперсет разумных полей (условие
приёма ID+маска+данные+маска данных+канал, ответ ID+данные+канал+задержка,
включён/выключен), достаточных для реализации логики, аналогичной уже работающей
на ПК `ui/can_trigger_tab.py`.

### 2.5 CMD_TRIGGER_WRITE (0xC4) — запись одного триггера

Запрос: `[0xC4][len][index:1][trigger_payload]`. Ответ: `[0xD4][status][0x00]`.

### 2.6 CMD_TRIGGER_ENABLE (0xC5) — включить/выключить триггер без перезаписи

Запрос: `[0xC5][0x02][index:1][enabled:1]`. Ответ: `[0xD5][status][0x00]`.

**Нумерация каналов в `trigger_t`** — 0-based, как индекс комбобокса UI:
`rx_channel`/`tx_channel`: `0` = CAN1, `1` = CAN2, `2` = «CAN1 и CAN2»
(на приём матчит кадр с любого канала, на ответ шлёт фрейм в оба канала).
Это отличается от wire-нумерации CAN-кадров (1/2) — `CanBridge` внутри
прошивки хранит кадры с 0-based каналом, а конверсия в wire-формат
происходит только при отправке ответа триггера.

### 2.7 CMD_CAN_ERROR_STATUS (0xC6) — статус ошибок/bus-off шины CAN

Добавлено при исправлении находки аудита (CURSOR_FIX_PROMPT.md 4.4): раньше
`can_bridge.c` включал только `CAN_IT_RX_FIFO0_MSG_PENDING` — `AutoBusOff`
(см. `configure_bit_timing()`) восстанавливает bxCAN аппаратно сам, но ни
firmware, ни ПК никогда не узнавали, что шина вообще уходила в bus-off или
ловила ошибки (например, из-за плохого/отсутствующего терминатора).

Запрос: `[0xC6][0x01][channel:1]` (`channel`: 1 = CAN1, 2 = CAN2).

Ответ: `[0xD6][status][0x06][had_error:1][had_busoff:1][last_error_code:4 LE]`

- `had_error` — 1, если после предыдущего опроса этого канала произошла хотя бы
  одна ошибка шины (stuff/form/ACK/bit/CRC, error-warning, error-passive или
  bus-off — см. `HAL_CAN_ERROR_*` в `stm32f1xx_hal_can.h`); флаг сбрасывается
  чтением, как и флаг переполнения RX-кольца (`CanBridge_TookOverflow()`).
- `had_busoff` — отдельный «липкий» флаг: 1, если канал хотя бы раз уходил в
  Bus-Off с прошлого опроса (сбрасывается чтением). `AutoBusOff` восстановит
  шину автоматически, но ПК всё равно стоит предупредить пользователя.
- `last_error_code` — сырой битовый код HAL, зафиксированный на момент
  последней ошибки (диагностика; конкретные биты см. `HAL_CAN_ERROR_*`).

ПК должен опрашивать эту команду периодически (например, в фоне вместе с
чтением CAN-кадров) — иначе кратковременные ошибки между опросами будут
потеряны (флаги сбрасываются чтением, история не хранится).

### 2.8 CMD_CAN_STATS (0xC7) — накопительные счётчики CAN

Запрос: `[0xC7][0x01][channel:1]` (`channel`: 0 = CAN1, 1 = CAN2).

Ответ payload длиной 24 байта:

```text
rx_count:     uint32 LE — принятые CAN-кадры
tx_count:     uint32 LE — успешно переданные CAN-кадры
lost_count:   uint32 LE — кадры, отброшенные из-за переполнения RX ring
error_count:   uint32 LE — CAN error interrupts
busoff_count:  uint32 LE — переходы в bus-off
recovery_count:uint32 LE — автоматические восстановления после bus-off
```

Host должен принимать и старый 12-байтный ответ для совместимости.

Счётчики монотонные до перезапуска устройства. Команда их не очищает.

### 2.9 CMD_TRIGGER_STAGE (0xCA) и CMD_TRIGGER_COMMIT (0xCB)

`CMD_TRIGGER_STAGE` принимает `[index:1][trigger_t:54]`, проверяет запись и
сохраняет её только в RAM. `CMD_TRIGGER_COMMIT` принимает пустой payload и
одной операцией стирает/записывает trigger page со всеми staged-изменениями.
При ошибке Flash RAM-состояние откатывается к предыдущей копии.

### 2.10 CMD_USB_STATS (0xCC) — потерянные USB CDC TX-передачи

Запрос: `[0xCC][0x00]`.

Ответ payload: `tx_dropped: uint32 LE`. Счётчик увеличивается при TX timeout
или отказе USB CDC передачи и сохраняется до перезапуска устройства.

### 2.11 CMD_SYSTEM_INFO (0xC9) — информация о системе

Запрос: `[0xC9][0x00]`.

Ответ payload: минимум 16 байт (базовая часть), актуальные прошивки — 56 байт:

```text
offset 0  application_version: uint8
offset 1  protocol_version:    uint8
offset 2  flash_size_kb:       uint16 LE
offset 4  config_format:       uint8
offset 5  config_record_length:uint8
offset 6  trigger_count:       uint8
offset 7  config_valid:        uint8
offset 8  application_size:    uint32 LE
offset 12 application_crc32:   uint32 LE
offset 16 mcu_uid96:           12 байт (Unique Device ID, 0x1FFFF7E8)
offset 28 build_datetime:      20 байт ASCII ("Mmm dd yyyy hh:mm:ss")
offset 48 git_commit:          8 байт ASCII (короткий hash, с нулями)
```

Читатель обязан проверять длину payload: старые прошивки отвечают
ровно 16 байтами и не содержат полей после offset 15.

## Часть 3 — формат хранения конфигурации во Flash («страница А»)

В ТЗ 11.2 «область страницы А» означает отдельную страницу конфигурации
устройства, а не последнюю физическую страницу Flash: последние страницы
зарезервированы под триггеры. Не путать её со страницей разделения
бутлоадера/приложения. Используется отдельная страница, не пересекающаяся
с образом кода приложения, чтобы прошивка нового `.bin`/`.hex` не требовала
пересохранения имени/серийника при каждом обновлении (конфигуратор трогает Flash
конфигурации только явно, по ТЗ 11.3).

Карта Flash (STM32F105RCT6, 256 KB, страница = 2048 байт, подтверждено в
`firmware/bootloader/Src/bootloader.c`):

| Адрес | Размер | Назначение |
|---|---|---|
| `0x08000000`–`0x08007FFF` | 32 KB (стр. 0–15) | Бутлоадер (не трогать) |
| `0x08008000`–`0x0803CFFF` | 212 KB (стр. 16–122) | Приложение (код) |
| `0x0803D000`–`0x0803D7FF` | 2 KB (стр. 122) | Метаданные целостности application (CRC32/размер) |
| `0x0803D800`–`0x0803DFFF` | 2 KB (стр. 123) | **Конфигурация устройства** (имя/serial/VID/PID) |
| `0x0803E000`–`0x0803FFFF` | 8 KB (стр. 124–127) | Триггеры (10 × 54 байт в одной странице, остальное — запас) |

Первые 212 KB после bootloader отданы под код application. Следующая
страница зарезервирована под метаданные целостности: bootloader хранит там
magic, версию, размер образа и CRC32. Конфигурация и триггеры находятся в
отдельных страницах и не должны попадать в linker FLASH region.

Формат страницы метаданных application (`0x0803D000`):

```
offset 0  : uint32_t magic         (0x41505031 = "APP1")
offset 4  : uint16_t version        (1)
offset 6  : uint16_t reserved
offset 8  : uint32_t image_size     (байт от 0x08008000)
offset 12 : uint32_t crc32         (CRC-32/IEEE по image_size байтам)
```

Bootloader проверяет метаданные строго: application запускается только при
валидном magic + совпавшем CRC32. Стёртая страница (0xFF), обнулённый magic
(0x00 — записывается конфигуратором в начале обновления, «UPDATE_STARTED»)
или незаписанная запись означают «обновление не завершено» — устройство
остаётся в bootloader. Метаданные всегда пишутся последним шагом, после
кода и верификации — это «флаг завершённого обновления» («UPDATE_VERIFIED»).

Через AN3155 разрешены запись и постраничное стирание только для
`0x08008000`–`0x0803DFFF` (application + metadata + config). Область
триггеров `0x0803E000`–`0x0803FFFF` через AN3155 недоступна — триггеры
обновляются только командами CMD_TRIGGER_STAGE/COMMIT. Mass erase (0xFFFF)
по-прежнему стирает весь application-регион целиком.

Формат страницы конфигурации (`device_config_t`, см. `Inc/device_config.h`):

```
offset 0   : uint32_t magic         (0x43464730 = "CFG0")
offset 4   : uint8_t  device_name_len
offset 5   : char     device_name[9]
offset 14  : uint8_t  serial_len
offset 15  : char     serial[10]
offset 25  : uint16_t vid
offset 27  : uint16_t pid
offset 29  : uint8_t  format_version (0 = legacy, 1 = current)
offset 30  : uint8_t  record_length  (32 for current format)
offset 31  : uint8_t  crc8          (CRC-8, полином 0x07, по байтам offset 0..30)
```

Всего 32 байта, выровнено под half-word запись HAL (`HAL_FLASH_Program` с
`FLASH_TYPEPROGRAM_HALFWORD`, как в существующем `bootloader.c`). При `magic` или
`crc8` не совпадающих с ожидаемым — конфигурация считается «пустой» (заводское
состояние), используется значение по умолчанию (см. `device_config.c`:
`device_name="CodeMaster"` обрезано до 9 симв. → `"CodeMaste"`, `serial=""`,
`vid=0x0483`, `pid=0x5740`).

**Важно (эксплуатационное ограничение, зафиксировать как допущение):** запись
одной страницы Flash требует предварительного стирания всей страницы (2 KB), что
занимает единицы–десятки миллисекунд — на это время прерывания HAL Flash
блокируют весь main-loop (это ограничение периферии, не прошивки). Поэтому
CMD_CFG_WRITE/CMD_TRIGGER_WRITE не должны вызываться на устройстве, когда идёт
активная передача CAN на 100% загрузке шины — приём в это время будет
буферизован в кольцевые буферы CAN (см. Часть 4 в README) и не потеряется при
разумной длительности стирания (≤20 мс на страницу при 512-глубоких буферах и
14000 пак/с это ~7 кадров запаса на канал, что укладывается в буфер, но близко
к пределу — задокументировано как риск в README).
