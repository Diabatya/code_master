# CM-F04 — USB-имя и работа без COM

Отчёт по пункту задания CM-F04. Исправление идентичности —
в этом коммите; переход на без-COM транспорт — отдельный этап
(по уточнению владельца: сначала рабочий CDC и автономная ГЛ).

## 1. Идентичность iProduct/iSerial — что было и что стало

| Режим | Было | Стало |
| --- | --- | --- |
| Приложение (PID 0x5740) | iProduct = `device_name` из CFG0 («Тип устройства», ≤9 ASCII), iSerial = `serial` из CFG0 (≤10 ASCII), фолбэк «CodeMaster CAN»/UID | без изменений — уже тип устройства |
| Загрузчик (PID 0x5741) | iProduct = «CodeMaster Bootloader», iSerial = из 96-бит UID | iProduct/iSerial из той же записи CFG0 (страница `0x08008000`, легаси `0x0803D800` вторым чтением); фолбэк «CodeMaster Bootloader»/UID при отсутствии записи |

Реализация: `firmware/bootloader/Src/device_identity.c` —
read-only парсер записи CFG0 (magic + CRC8 poly 0x07, формат
`device_config_t` приложения). Загрузчик страницу только читает;
запись — только сервисным DFU/ST-Link (контракт CM-F03).
Покрытие: `firmware/application/tests/test_device_identity.c`
(валидная запись, битый CRC, легаси-фолбэк, приоритет новой
страницы) + CI build.yml.

**Следствие для маршрутов обновления:** загрузчик изменился →
существующие платы получают его только полным DFU-образом
(маркировка 111 — CM-F12). Плата на старом загрузчике продолжает
работать, просто показывает прежнее имя в режиме обновления.

### Ограничения (честные)

- Windows кэширует «friendly name» и складывает записи по
  VID/PID/serial: после прошивки нового загрузчика первая
  энумерация может показать закэшированное старое имя. Корректный
  дескриптор сам по себе не меняет текст уже созданных узлов
  Диспетчера устройств — это свойство Windows, не дескриптора.
- Проверка «человеческого» отображения (Диспетчер устройств,
  уведомления, «Безопасное извлечение») на Windows 10/11 **не
  выполнялась** — нет стенда Windows. По коду: обе строки из CFG0
  ограничены ТЗ (9/10 ASCII) и конвертируются в UTF-16LE штатным
  `USBD_GetString` — усечения/переполнения нет.
- Разные экземпляры различаются по iSerialNumber — с этого
  коммита загрузчик и приложение одного экземпляра отдают
  ОДИНАКОВЫЙ серийник (раньше загрузчик показывал UID-производный
  → Windows видела «другое устройство» при переходе в обновление).

## 2. Исследование: USB без COM-порта (отдельный этап)

### Вариант, рекомендуемый к проработке: WinUSB (vendor-specific bulk)

- **Принцип.** Устройство отдаёт Microsoft OS 2.0 Descriptors
  (BOS + set-дескрипторы с GUID интерфейса). Windows 8.1+
  автоматически ставит встроенный WinUSB-драйвер без INF и без
  сертификации. COM-порта в системе нет физически — транспорт
  vendor-specific bulk/interrupt.
- **Хост.** На Windows — WinUSB API (или `libusb`/`pyusb`);
  macOS/Linux — `libusb`/`pyusb` без драйверов (CDC там и так
  работает без установки, но единый vendor-транспорт упрощает
  кодовую базу).
- **Discovery.** Перечисление по VID/PID + GUID интерфейса +
  iSerial → автоматическое подключение без выбора порта; два
  одинаковых устройства различаются серийником (он уже есть в
  CFG0 и теперь един для обоих режимов).
- **Объём прошивки.** Замена CDC-класса на vendor-класс:
  ~2 bulk EP вместо CDC пары, дескрипторы MS OS 2.0 (~200 Б),
  свой «class» файл вместо `usbd_cdc.c`. На STM32F105 FS-USB
  помещается без изменения карты памяти.
- **Загрузчик.** Тот же интерфейс WinUSB → обновление без
  переименования портов вообще; но потеря CDC убирает
  «пульт аварийного восстановления» через любой терминал —
  срезать CDC с уже прошитых плат нельзя, пока нет проверенного
  маршрута восстановления.

### Риски и границы проверки

| Риск | Комментарий |
| --- | --- |
| Первое подключение Windows | MS OS 2.0 descriptors читаются один раз при энумерации; ошибка в BOS = невидимое устройство. Нужен стенд Windows 10/11 |
| Два одинаковых устройства | Требуется проверка: разные экземпляры одного VID/PID по серийнику |
| Переход app↔bootloader | Сохранять серийник/GUID в обоих режимах — уже заложено единой идентичностью из CFG0 |
| Пакетная задержка | CDC даёт тот же bulk-транспорт; скорость канала не упрётся в класс, но CAN-поток требует проверки таймингов |
| macOS/Linux/упаковка | `pyusb`/`libusb` тащатся в сборку; macOS требует entitlement/подписи для low-level USB? — проверить на сборке |
| Откат | Плата без CDC, у которой WinUSB-интерфейс не взвёлся, восстанавливается только DFU — маршрут DFU должен быть описан раньше миграции |

### Статус

Реализация не начата по уточнению владельца («сначала CDC»). Этот
документ — граница исследования: техническая оценка, не
подтверждение готовности конкретной платы. Перед миграцией нужен
список проверок: авто-установка WinUSB на чистой Windows,
discovery двух экземпляров, полный цикл обновления без COM,
recovery-сценарии.
