# Аудит проекта «Код Мастер» — архитектура, качество кода, зависимости

**Дата аудита:** 20.08.2026
**Тип аудита:** независимый технический аудит (архитектура / качество кода / инфраструктура), без изменения кода.
**Отличие от предыдущих аудитов:** `AUDIT_REPORT.md` и `AUDIT_REPORT_V2.md` проверяли функциональную полноту UI (реализована ли фича по ТЗ). Этот аудит смотрит на проект с инженерной стороны — сопровождаемость, риски, гигиену репозитория. Выводы не пересекаются с предыдущими отчётами.

Проект: PySide6-приложение для диагностики CAN-шины и прошивки STM32 (UART/USB DFU/ST-Link/J-Link). ~16 300 строк в `core/`, `ui/`, `models/`, 49 Python-файлов. Самые крупные модули: `ui/flash_dialog.py` (1855 строк), `ui/can_monitor_tab.py` (1173), `ui/can_trigger_tab.py` (954).

---

## 1. Архитектура и структура кода

### Сильные стороны

- **Протокольный слой корректно изолирован от Qt** в ключевых местах: `core/bootloader.py` и `core/dfu.py` не зависят от PySide6, принимают уже открытый порт — это единственный код в проекте, который реально можно юнит-тестировать без GUI-окружения.
- **`models/config.py`** — потокобезопасный синглтон с double-checked locking и атомарной записью файла (tmp + `os.replace`) — реализация выше среднего уровня для такого паттерна.
- **`core/serial_manager.py`** общается с UI только через Qt-сигналы (`new_can_frame`, `error_occurred` и т.д.), без прямых обращений к виджетам из фонового потока — потокобезопасность на уровне UI-интеграции соблюдена.
- **`main.py`** компактен (135 строк), CLI-режим прошивки логически отделён от GUI-пути.

### Проблемы

| Серьёзность | Находка |
|---|---|
| **Критично** | Утечка serial-протокола в UI: `ui/flash_dialog.py` в трёх классах-воркерах (`ConnectWorker`, `FlashWorker`, `ReadWorker`) напрямую создаёт `serial.Serial(...)` с настройкой baudrate/parity/bytesize (строки ~582, 622, 807, 858, 1049, 1078), минуя `SerialManager`. Та же последовательность настройки порта продублирована третий раз в `main.py:_cli_flash` (строки 60-67). Протокол прошивки нигде не переиспользуется и недоступен вне Qt-потоков. |
| **Критично** | `ui/flash_dialog.py` — God Object: 1855 строк совмещают HEX-редактор (`HexHighlighter`, `HexEditorDialog`), три протокольных QThread-воркера и сам UI-диалог. Разделение на отдельные модули (виджет редактора / воркеры-адаптеры к core / диалог) устранило бы и это, и предыдущий пункт. |
| **Критично** | Тестов бизнес-логики нет вовсе (см. раздел 2). Причина архитектурная: протокол прошивки вплетён в `QThread`-подклассы внутри UI-файла, поэтому его нельзя протестировать без Qt event loop и без мокинга самого UI-класса. |
| Средне | `Config()` инстанцируется напрямую (не через DI) в 15+ файлах `ui/*.py`, ~267 обращений `.get()/.set()` в 21 файле — классическое глобальное изменяемое состояние. Работает, но исключает возможность подменить конфиг в тестах и затрудняет отслеживание, кто и когда меняет какое поле. |
| Средне | Копипаста и рассинхронизация HEX/ID-валидации между похожими вкладками: `ui/can_trigger_tab.py` использует собственный `_IdValidator` (свои строки 43-88), а `ui/can_gateway_tab.py` и `ui/flexible_logic_tab.py` используют «голый» `hex_to_int` без валидации вообще. Общего базового класса/миксина нет — поведение полей ID отличается между вкладками, которые внешне выглядят одинаково. |
| Незначительно | `ui/flexible_logic_tab.py` импортирует `DbcSignalDialog` напрямую из `ui/can_monitor_tab.py` — межвкладочная связь внутри UI-слоя вместо переноса общего диалога в отдельный модуль; при дальнейшем росте UI это создаёт почву для циклических импортов. |

## 2. Качество кода и потенциальные баги

- **`ruff`** установлен (есть `.ruff_cache`), но конфигурация (`pyproject.toml`/`ruff.toml`) в репозитории отсутствует — линт фактически работает «на дефолтах» либо через параметры, не зафиксированные в проекте. Стоит закоммитить явный конфиг, чтобы правила линтинга были воспроизводимы у всех разработчиков и в CI.
- **`python3 -m py_compile`** проходит без ошибок по всем 49 файлам — синтаксически проект чист.
- **Обработка исключений** в целом аккуратная: голых `except: pass` в критичных путях (запись прошивки) не найдено — везде `except Exception as exc` с логированием/пробросом. «Тихие» `except Exception: pass` встречаются только в cleanup-коде (закрытие портов/соединений в `__del__`, disconnect) — это приемлемо.
- **Потокобезопасность `SerialManager`, средне:** `Lock` защищает только `send_data()`. Методы идентификации устройства (`ping_device`, `_detect_device_id`, `auto_detect_can_speed`, `core/serial_manager.py` ~304-453) читают `self._port` без лока; `_stop_reader()`/`_start_reader()` пересоздают `self._reader` также без удержания лока. При конкурентном вызове `send_data()` и, например, `auto_detect_can_speed()` из разных потоков возможна гонка за `self._port`. На практике вызовы обычно последовательны из UI-потока, но явной защиты нет.
- **Потенциально критичный баг в `ui/flash_dialog.py::_prepare_config_only_hex` (~строки 1380-1407):** размер страницы flash захардкожен как `2048` независимо от реально выбранной модели STM32 в `STM32_PAGE_SIZES` (у STM32F103 страница 1024 байт, у STM32F2/F4 — 16384). Если пользователь выбрал чип с другим размером страницы, `last_page = flash_size - 2048` может указать не на последнюю физическую страницу, а на середину прошивки — риск **затереть часть валидной прошивки при записи конфигурации устройства**. Это единственная находка, которая может реально «окирпичить» устройство, и её стоит проверить в первую очередь.
- **Несогласованность базовых адресов записи:** UART/USB CDC путь использует `0x08008000`, а ST-Link/J-Link/DFU — `0x08000000` (разные смещения в разных методах `ui/flash_dialog.py`, не задокументировано в UI). Если пользователь путает интерфейс прошивки для одного и того же файла, результат попадёт по разным адресам без предупреждения.
- **`core/bootloader.py::erase_pages`** (в отличие от `dfu.py`) не имеет предохранителя `skip_blank = len(data) < flash_size` — при частичной прошивке через UART-путь высок риск оставить «хвост» старой прошивки на непереписанных страницах.
- **Магические числа:** адрес `0x08000000`/`0x08008000` захардкожен минимум в 9+ местах без единой константы `FLASH_BASE_ADDRESS`. USB VID `0x0483` продублирован как литерал в `bootloader.py` и `dfu.py` отдельно, без общего `usb_ids.py`. Таблицы `STM32_FLASH_SIZES`/`STM32_PAGE_SIZES`/`DEVICE_ID_TO_MODEL` живут в UI-модуле (`ui/flash_dialog.py:80-114`), а логически это справочные данные о железе и место им — в `core/`.
- **TODO/FIXME/XXX** — в коде не найдено ни одного (не обязательно плюс: может означать, что незавершённые куски не помечаются, а просто остаются как есть).
- **Docstring/типизация:** `core/can_protocol.py`, `models/config.py`, `ui/main_window.py` — высокое покрытие (95-100%). `ui/can_trigger_tab.py` — только 43% функций с docstring при 100% type hints, то есть аннотации есть, а описание поведения — нет, именно в самом сложном UI-файле после `flash_dialog.py`.
- **Мусорные файлы в корне репозитория, подтверждено через `git log`:** `reliz1.hex` (37 КБ, прошивка), `ОПР 2026.03 телефоны.xlsx`, `ОПР список образец.xlsx`, `Учет внутренних тренеров_2600.xlsx` (385 КБ) — три последних физически лежат в рабочей копии и **не в `.gitignore`**, при этом `Учет внутренних тренеров_2600.xlsx` уже закоммичен в истории git (см. раздел 3) — потенциальная утечка персональных/внутренних данных компании в репозиторий с историей кода прошивки автомобильной электроники.

## 3. Зависимости и инфраструктура

- **`.gitignore` работает частично:** `build/`, `dist/`, `.venv/`, `__pycache__/` в git не попадают — это хорошо. Но **`reliz1.hex` и устаревший `CodeMaster.spec`** уже закоммичены и являются мусором (не используются в CI, дублируют `build_*.spec`). `.ruff_cache/`, `*.hex`, `*.xlsx` не добавлены в `.gitignore`.
- **Размер `.git` — 46 МБ**, не критично, но самый тяжёлый объект в истории — `Учет внутренних тренеров_2600.xlsx` (385 КБ, личные/внутренние данные). Основной вклад в размер — 16+ ревизий `ui/flash_dialog.py` по 60-78 КБ каждая, что косвенно подтверждает — файл слишком часто и много правится целиком из-за своего размера (см. раздел 1).
- **Критично: версии зависимостей без верхней границы.** Все 11 пакетов в `requirements.txt` заданы через `>=` (`PySide6>=6.5`, `pyocd>=0.36.0` и т.д.), lock-файла нет. CI на каждой сборке подтягивает последние доступные версии без ревью — мажорный breaking change в PySide6 или pyocd может попасть прямо в релизную сборку никем не замеченным.
- **Критично: в CI (`.github/workflows/build.yml`) нет ни одного шага lint/test** перед сборкой релиза. При этом сам workflow технически современный: актуальные версии actions (checkout@v5, setup-python@v6), Python 3.12 зафиксирован, PyInstaller запинен `<7.0`. Отсутствует кэширование pip-зависимостей (не критично, влияет на скорость). Политика релиза агрессивная: **каждый push в `main` перезаписывает pre-release `latest`** — нет staging/draft-этапа.
- **Средне: три spec-файла (`build_win/mac/linux.spec`)** не имеют общего источника списка `hiddenimports` — списки почти идентичны, но правятся вручную и независимо, реальный риск рассинхронизации при добавлении нового модуля (баг «работает на Windows, падает на Linux»).
- **Критично для UX, не для кода:** приложение зависит от системных USB-драйверов (Zadig/WinUSB для ST-Link на Windows, udev-правила на Linux для pyusb/libusb), но ни в `README.md`, ни в `USER_GUIDE.md` это нигде не упомянуто — пользователи будут получать необъяснимые ошибки доступа к USB-устройству.
- **Средне: `NOTICE.md`** корректно упоминает `commaai/opendbc` (MIT), но не упоминает `iDoka/awesome-automotive-can-id`, хотя данные из этого проекта используются в `library/can_id/` — пропуск атрибуции стороннего контента.
- **Средне: нет Dependabot/Renovate** — в сочетании с отсутствием пинов версий это означает полное отсутствие контроля за устареванием/уязвимостями зависимостей.

## 5. Рекомендации по приоритету

**Сначала (риск для пользователя/данных):**
1. Проверить и исправить логику `page_size` в `_prepare_config_only_hex` относительно реального `STM32_PAGE_SIZES` выбранного чипа.
2. Удалить из git и рабочей копии личные xlsx-файлы и `reliz1.hex`, добавить правила в `.gitignore`, при необходимости очистить историю (BFG/git-filter-repo) от `Учет внутренних тренеров_2600.xlsx`.
3. Зафиксировать версии зависимостей (пины или верхние границы) и добавить шаг `pytest`/`ruff check` в CI перед сборкой релиза.

**Затем (сопровождаемость):**
4. Вынести протокол прошивки из `ui/flash_dialog.py` в `core/` (общий с CLI-режимом), разбить файл на HEX-редактор / протокольные адаптеры / диалог.
5. Добавить unit-тесты для core-модулей, которые уже не зависят от Qt (`core/bootloader.py`, `core/dfu.py`, `core/can_protocol.py`) — они готовы к тестированию уже сейчас.
6. Унифицировать HEX/ID-валидацию в общий виджет/миксин для триггеров, шлюза и гибкой логики.

**Позже (гигиена):**
7. Задокументировать установку драйверов (Zadig/udev) в USER_GUIDE.md.
8. Централизовать константы адресов flash и USB ID.
9. Добавить Dependabot, синхронизировать hiddenimports между тремя spec-файлами (общий Python-модуль со списком), дополнить NOTICE.md.
