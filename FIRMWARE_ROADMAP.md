# Дорожная карта развития firmware и конфигуратора «Код Мастер»

Документ описывает рекомендуемые улучшения для текущей системы STM32 + USB/CAN + desktop-конфигуратор.

Цели:

- сделать обновление firmware безопасным и восстанавливаемым;
- синхронизировать настройки устройства между МК и ПК;
- обеспечить диагностику CAN/USB и потерь кадров;
- сохранить совместимость bootloader и существующих wire-форматов;
- подготовить систему к длительной эксплуатации и серийному производству.

---

## 1. Текущая архитектура

Система состоит из двух образов:

| Образ | Адрес | Назначение |
|---|---:|---|
| Bootloader | `0x08000000–0x08007FFF` | Запуск application, USB CDC/AN3155, обновление и чтение Flash |
| Application | `0x08008000–0x0803D7FF` | CAN-мост, USB CDC, триггеры и основной протокол |
| Конфигурация | `0x0803D800–0x0803DFFF` | Имя, serial, VID/PID, magic, CRC8 |
| Триггеры | `0x0803E000–0x0803FFFF` | 10 структур триггеров по 54 байта |

Текущие исходники:

- `firmware/bootloader/` — загрузчик;
- `firmware/application/` — основная прошивка;
- `firmware/PROTOCOL.md` — описание wire-протокола;
- `core/bootloader.py` — AN3155-клиент;
- `core/dfu.py` — USB ROM DFU;
- `ui/flash_dialog.py` — окно прошивки и чтения;
- `core/can_protocol.py` — базовые команды USB/CAN;
- `core/serial_manager.py` — COM/USB CDC обмен.

---

# 2. Приоритет P0: безопасность обновления

## 2.1. Проверка целостности application в bootloader

### Зачем

Сейчас bootloader должен отличать корректную application от повреждённой. При обрыве питания во время записи application устройство не должно переходить в повреждённый код.

### Что добавить

В bootloader:

1. Проверку начального значения MSP:
   - адрес должен находиться в допустимом диапазоне RAM;
   - для STM32F105 — в области `0x20000000`.
2. Проверку reset vector:
   - адрес должен находиться внутри `0x08008000–0x0803D7FF`;
   - младший бит Thumb должен быть установлен.
3. Проверку длины application.
4. Проверку CRC32 или другого согласованного checksum.
5. Флаг `application_valid`.
6. Установку флага только после полной записи и успешной проверки.

### Результат

- повреждённая прошивка не запускается;
- устройство остаётся в bootloader;
- конфигуратор может повторить обновление;
- снижается риск «кирпича» после обрыва USB или питания.

### Ограничение

Нельзя менять существующий AN3155 wire-формат без необходимости. Проверка целостности должна быть дополнительной логикой bootloader/образа.

---

## 2.2. Восстановление после прерванной прошивки

### Зачем

При отключении питания в середине записи приложение может быть записано частично.

### Что добавить

- журнал последнего успешно записанного блока;
- размер ожидаемого образа;
- CRC ожидаемого образа;
- состояние `UPDATE_STARTED`, `UPDATE_IN_PROGRESS`, `UPDATE_VERIFIED`;
- возможность продолжить запись с последнего блока или безопасно начать заново;
- автоматический возврат в bootloader, если `UPDATE_VERIFIED` не установлен.

### Результат

После обрыва питания устройство не запускает неполную application и восстанавливается повторной прошивкой.

---

## 2.3. Защита от выхода за границы памяти

### Что проверить

Bootloader должен запрещать запись в:

- область bootloader `0x08000000–0x08007FFF`;
- конфигурацию при обычной прошивке application;
- область триггеров при обычной прошивке application;
- адреса выше `0x0803FFFF`.

### Результат

Ошибочный BIN/HEX не сможет стереть bootloader, конфигурацию или триггеры.

---

## 2.4. Проверка перед запуском application

Добавить в bootloader понятные причины отказа запуска:

- `APP_EMPTY`;
- `APP_INVALID_VECTOR`;
- `APP_CRC_ERROR`;
- `APP_UPDATE_INCOMPLETE`;
- `APP_OUT_OF_RANGE`.

Эти статусы желательно показывать в конфигураторе при подключении.

---

# 3. Приоритет P1: конфигурация устройства

## 3.1. Версия структуры конфигурации

### Зачем

Сейчас есть `magic` и CRC8, но при расширении структуры потребуется отличать старый формат от нового.

### Что добавить

В конфигурационную запись:

```text
magic
format_version
record_length
device_name_len
device_name
serial_len
serial
VID
PID
reserved
CRC8
```

### Результат

Можно добавлять новые поля без поломки старых устройств.

---

## 3.2. Миграция старых конфигураций

### Что сделать

При старте application:

1. Проверить текущий magic.
2. Определить версию формата.
3. Если найден старый формат — преобразовать его в новый.
4. Записать новый формат только после успешной проверки.
5. Сохранить имя и serial, если они доступны.

### Результат

Старые платы переходят на новый формат без ручного редактирования Flash.

---

## 3.3. Снижение износа Flash

Перед `CMD_CFG_WRITE` и `CMD_TRIGGER_WRITE` сравнивать новые данные с текущими.

Если данные не изменились:

- не стирать страницу;
- не выполнять запись;
- не перезапускать USB;
- вернуть успешный статус без цикла Flash.

### Результат

Меньше циклов стирания Flash и меньше времени на конфигурацию.

---

## 3.4. Резервное копирование конфигурации

В конфигураторе добавить:

- «Экспорт конфигурации»;
- «Импорт конфигурации»;
- формат JSON или `.cmm`;
- отображение версии формата;
- проверку CRC перед импортом.

### Результат

Имя, serial, VID/PID и настройки можно переносить между устройствами.

---

# 4. Приоритет P1: триггеры

## 4.1. Полная синхронизация триггеров с устройством

Firmware уже содержит команды:

```text
CMD_TRIGGER_READ   0xC3
CMD_TRIGGER_WRITE  0xC4
CMD_TRIGGER_ENABLE 0xC5
```

Нужно добавить в конфигуратор:

- «Прочитать триггеры из устройства»;
- «Записать текущий триггер»;
- «Записать все триггеры»;
- «Включить/выключить триггер»;
- «Сравнить ПК и устройство»;
- «Восстановить триггеры из файла».

### Результат

Настройки в интерфейсе и настройки внутри МК перестанут расходиться.

---

## 4.2. Версия формата trigger_t

Добавить:

- версию структуры;
- размер структуры;
- CRC каждой записи или всей страницы;
- проверку границ значений;
- обработку неизвестной версии.

### Результат

Будущие изменения полей триггера не повредят старые сохранённые данные.

---

## 4.3. Защита от повреждения страницы триггеров

Рекомендуемая схема:

- две копии страницы конфигурации триггеров;
- sequence number;
- CRC страницы;
- запись новой копии перед стиранием старой;
- выбор последней корректной копии при старте.

### Результат

Отключение питания во время записи триггера не уничтожит все триггеры сразу.

---

# 5. Приоритет P1: диагностика CAN

## 5.1. Счётчики CAN

Добавить в firmware и протокол:

- принятые кадры CAN1/CAN2;
- переданные кадры CAN1/CAN2;
- потерянные кадры;
- переполнение RX ring buffer;
- CAN error count;
- bus-off count;
- количество автоматических восстановлений;
- последняя причина ошибки.

### Результат

Пользователь видит не только «связь есть», но и реальное состояние шины.

---

## 5.2. Отдельный статус переполнения

`CanBridge_TookOverflow()` необходимо подключить к диагностической команде или расширить новый диагностический ответ.

Рекомендуемый ответ:

```text
channel
had_error
had_busoff
overflow_count
last_error_code
rx_count
tx_count
```

Изменять старые C0–C5 нельзя. Новые диагностические поля следует добавить в новую версию C6 или отдельную команду.

---

## 5.3. Диагностика в UI

Добавить окно:

```text
CAN1
  RX:
  TX:
  Lost:
  Errors:
  Bus-off:

CAN2
  RX:
  TX:
  Lost:
  Errors:
  Bus-off:
```

Обновлять данные каждые 0,5–1 секунду.

---

# 6. Приоритет P1: производительность CAN и USB

## 6.1. Измерение реальной нагрузки

Проверить на железе:

- CAN1 100% загрузка;
- CAN2 100% загрузка;
- USB CDC непрерывный поток;
- одновременно активные триггеры;
- запись CSV на ПК;
- длительность теста 10–30 минут.

### Результат

Получить фактические значения:

```text
frames/sec
lost frames
USB throughput
CAN errors
buffer overflow count
CPU load
```

---

## 6.2. Улучшение USB CDC очереди

Проверить:

- отказ `CDC_Transmit_FS()` при занятом TX;
- переполнение TX buffer;
- потерю CAN-ответов;
- корректность повторной передачи;
- реакцию при закрытом COM-порту.

Рекомендуется использовать:

- TX ring buffer;
- фоновую отправку из main loop;
- счётчик потерянных USB сообщений;
- ограниченное время ожидания TX.

---

## 6.3. Предсказуемые таймауты

Все busy-wait циклы должны использовать `HAL_GetTick()` или hardware timer.

Нельзя использовать только счётчик итераций, зависящий от частоты CPU и оптимизации компилятора.

---

# 7. Приоритет P1: точность триггеров

Сейчас задержка использует `HAL_GetTick()`.

Для точных задержек добавить:

- TIM2/TIM3/TIM4 или другой свободный таймер;
- очередь событий с timestamp;
- аппаратное сравнение времени;
- измерение джиттера осциллографом или логическим анализатором.

### Результат

Достижение заявленной задержки и уменьшение зависимости от USB/CAN нагрузки.

---

# 8. Приоритет P2: информация о firmware

Добавить команду информации о системе:

```text

protocol_version
build_date
build_commit
mcu_id
flash_size
application_size
application_crc
config_status
```

```text

Application CRC: OK
Configuration: valid
Triggers: 10/10
```

### Результат

Быстрая диагностика платы без ручного чтения логов и исходников.

---

# 9. Приоритет P2: серийный номер и идентификация

Показывать отдельно:

- пользовательский serial;
- USB serial;
- уникальный 96-битный ID STM32;
- имя устройства;
- VID/PID.

Если пользовательская конфигурация повреждена, уникальный ID всё равно позволяет определить конкретную плату.

---

# 10. Приоритет P2: журнал обновления

Хранить в отдельной служебной области:

- время последней прошивки;
- размер образа;
- CRC образа;
- версия образа;
- результат последней проверки;
- код последней ошибки;
- количество попыток обновления.

Это упростит поддержку устройств у клиентов.

---

# 11. Приоритет P2: безопасность firmware

Для серийной эксплуатации рассмотреть:

- цифровую подпись firmware;
- проверку публичного ключа в bootloader;
- запрет неподписанных образов;
- защиту от downgrade;
- безопасное хранение ключа;
- журнал отказов проверки подписи.

Для лабораторной эксплуатации это можно отложить.

# 12. Драйверы и поставка

## Windows

Нужно документировать и проверять:

- CH340/CH341;
- CP210x;
- FTDI;
- USB CDC;
- WinUSB/libusb для STM32 ROM DFU;
- ST-Link USB driver/backend;
- SEGGER J-Link Software and DLL.

## Linux

Добавить и протестировать udev rules для:

- `0483:DF11`;
- `0483:5740`;
- `0483:5741`;
- ST-Link;
- J-Link.

## macOS

Проверить:

- USB CDC;
- ST-Link;
- J-Link DLL;
- libusb backend;
- запуск `.app` без установленного Python.

# 14. Критерии готовности версии для производства

Версия считается готовой, если:

- application CRC проверяется bootloader;
- повреждённая application не запускается;
- обновление восстанавливается после отключения питания;
- конфигурация читается и записывается без полной прошивки;
- старая конфигурация мигрирует или корректно помечается как устаревшая;
- триггеры синхронизируются между UI и МК;
- потери CAN отображаются пользователю;
- CAN1/CAN2 проходят нагрузочный тест;
- USB CDC проходит длительный тест;
- работают UART, USB CDC, USB DFU, ST-Link и J-Link;
- проверены драйверы Windows/macOS/Linux;
- `ruff`, `pytest`, `compileall`, обе firmware-сборки и PyInstaller проходят;
- есть резервная копия и процедура восстановления устройства.
